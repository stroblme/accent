# accent design guidelines

These rules cover the GTK4 + libadwaita desktop app, which is what exists today; each section also carries a Material 3 note so the Phase 3 Compose app starts from the same decisions instead of a second design pass. The precedents are Apostrophe and GNOME Text Editor: the note fills the window, the chrome stays out of the way, nothing is decorative. Where this document is silent the GNOME Human Interface Guidelines decide (<https://developer.gnome.org/hig/>, <https://developer.gnome.org/hig/principles.html>). Every URL below was checked and resolves.

## Principles

1. The note is the UI. Everything else is scaffolding that earns its pixels or disappears.
2. One accent colour, taken from the system. No second brand colour, no decorative chrome.
3. Every action is reachable from the keyboard, and the palette is the discoverable index of them.
4. Light and dark are the same design, not two designs. Same for the seven system accents.
5. The system owns fonts, colours, animation and scaling. We only own layout and behaviour.

## Layout map

Phase 1 widget choices. <https://developer.gnome.org/hig/patterns/containers/header-bars.html> · <https://developer.gnome.org/hig/patterns/nav/sidebars.html>

| Surface | Widget |
|---|---|
| Window shell | `AdwApplicationWindow` > `GtkPaned`, one `AdwToolbarView` per side, each with its own `AdwHeaderBar` |
| Header bars | two, so the sidebar reaches the top of the window and the tab bar spans only the editor column. Sidebar header: the start window controls, and otherwise empty. Main header: the sidebar toggle (always visible, so a collapsed sidebar can be brought back without the keyboard), `AdwWindowTitle` with vault name and note path, the Drawing toggle where the view-mode toggle used to be and only while a PDF is in front, primary menu, end window controls. Toggle Split View keeps its action, its chord and its place in the primary menu; what it lost is the button, a window having only so many places for one. What the window is busy with and what the file is went to the status bar: a header carries the document's name, not its facts. The main header takes over the start window controls when the sidebar is hidden |
| Sidebar | `AdwInlineViewSwitcher` in icon mode over an `AdwViewStack` of six equal panes: Files, Search, Tags, References, Git, Outline. Git shows itself only where there is a repository to talk about, so a vault that is not under version control keeps the switcher it had. **A vault always opens on Files**, whichever pane was showing when it was last closed: coming back to a search someone ran in another sitting is not where a vault starts. The switcher is the title widget of the sidebar's header bar, so the pane icons sit on the same line as the sidebar toggle and the mode group, and the tree's first row lines up with the tabs. Width is dragged on the `GtkPaned` handle, floor 200. The vault's own name sits above the tree as a plain label with a folder icon: it is what the listing is *of*, so there is nothing to open or expand, and it is the one root drop zone that is still on screen when the tree is scrolled too deep to have any blank area left. **Files lists every folder in the vault**, the ones the index deliberately does not walk included — `node_modules`, `__pycache__`, a `.venv`, a cargo `target/` — because a listing that silently leaves a folder out is one nobody can trust. Those rows are read straight off the disk, one level per expansion (`walk::unindexed_children`), and nothing else changes: the trees stay out of the index, the watcher and every query, so a 40 000-file `node_modules` costs nothing until someone opens the row. They are dimmed by the same rule the git-ignored rows are and for the same reason — search does not reach them — and they list and open but are never changed: no context menu, no drag out, no drop in, because a move the index never hears of would leave the tree and the index disagreeing until the next rescan. `.git` and `.trash` are out of reach here as everywhere. The merge happens where the files are (`Vault::list_dir`), so a vault on another machine gets it too. Everything else the walk indexes but the tree hides stays hidden: a dot-named path is not shown unless it is one of those trees. **The selection follows the open tab**, so the highlight says which file is in front rather than which row the pointer last crossed — GTK's single-click-activate also means *selected on hover*, and the two are one mechanism, so the open file's row is put back the moment the pointer leaves the list. Only among the rows already on screen: a shut folder is not opened and the list is not scrolled, which is what Reveal in Sidebar is for. **Files is a drag surface both ways**: a row dragged into a pane opens the note there and one dragged onto a pane's edge splits it, while a row dragged back into the tree moves the file — onto a folder into that folder, onto a file beside that file, onto the vault label or the blank area below the last row into the vault root, which is the same target that row's New Note would have used. Directories drag too. The two drags carry two content types: the plain string a pane opens, and a `GtkStringObject` only the tree's targets take, so a folder — which offers the second alone — can never be dropped into a pane and opened as a note. A move that cannot happen is refused while the pointer is still over the row, which simply does not light up: a folder onto itself, a folder into something under it, and anything into the folder it is already in. GTK's own `:drop(active)` outline is the whole of the feedback, and there is no insertion line. What is left goes through the same plan-and-rewrite Rename does, so open tabs follow the file and the links keep their confirmation. Search carries the entry on a line of its own, a row holding a `.linked` group of Match Case / Match Whole Word / Regular Expression / All toggles with the replace toggle at its far end, a revealer holding the replace field, and a progress bar between the controls and the results; the four toggles are text buttons (`Aa`, `Word`, `.*`, `All`) because Adwaita has no glyph for any of them, while the replace toggle is an icon because `edit-find-replace-symbolic` names exactly what it reveals. It sits outside the `.linked` group: the four change what the query means, it opens a panel. The search space by default is everything the index holds — every note plus every other text file under 1 MiB — minus what git ignores; `All` drops that exclusion in either mode, and reaches the trees the walk never entered (`node_modules`, a `.venv`, a `target/`) **in an exact search only** — the exclusion is a column, which the ranked query reads as well, while the skipped trees are a walk, and only the exact path makes it, at the cost of that walk per query. Its tooltip names both halves rather than promising the second one everywhere; forcing exact mode instead would turn a two-word ranked query into a literal-substring one, so asking for more files would quietly find fewer. Replace All rewrites notes, so the number on the button is the notes among the matches: the list shows every text file's hits, the button counts what it will write. `.git` and `.trash` are out of reach even then. **A note is never excluded, whatever ignores it**: a notes vault that gitignores its own `*.md` is the ordinary case, so every one of these filters carries an explicit markdown escape, and the file tree lists an ignored file dimmed rather than hiding it. There is no ignore file inside the vault: `.accentignore` was removed, and what a user wants left out is named in one place instead, `[search] exclude` in `config.toml` — a list of vault-relative directory paths that joins git's own answer in the same exclusion column, so it obeys every rule above, `All` still reaches it, the tree still dims it, a note inside it is still found, and a vault with no repository has an exclusion mechanism again. It does not replace `walk.rs`'s built-in skips, which are about what the index and the kernel's watch budget can hold rather than about what a reader wants to see. Tags splits its column on a second vertical `GtkPaned`, tag list above, the files carrying the selected tag in the lower third. References answers one question for two kinds of file: on a note it lists the notes that link to it, once each, because a note that links three times is one backlink; on a source file it lists every place the symbol under the caret is used, `path:line`, and follows the caret while the pane is on screen. Outline is an `AdwBin` rather than a list of its own, because what belongs in it is the open tab's business: the symbols the language layer names for the open file — a note's headings, a source file's functions and types, nested as the server nests them — the PDF viewer's bookmarks and thumbnails, and an empty state when there is nothing to outline. Its rows activate on a single click, and so does every other result list here — search hits, the files under a tag, the backlinks — as the file tree's rows and the Git pane's changed files already did: one click opens what a row stands for, which is how GNOME's own sidebars behave. What a click opens is the pane's **preview** tab, so walking a list of results replaces one tab instead of leaving twenty behind; a double-click on the tab, or the first edit, keeps it. A search hit that names a place in the file — every hit of an exact search does; a ranked one matched the note, not a spot in it — opens on that place and leaves the match marked, using the find bar's own marks, which last until a new query or an edit moves them |
| Git pane | one repository at a time, chosen in a `GtkDropDown` that hides itself when there is only one and whose button ellipsizes the name, a repository being named after its directory and that name otherwise deciding how narrow the whole sidebar can be dragged. Under it a branch row: the branch itself, in a second `GtkDropDown` built exactly like the repository one and listing the repository's local branches, so the readout is also the switch — picking one is `git switch`, and whether that is safe is git's call, its own first line coming back as a toast and the chooser going back to the branch HEAD is really on where it refuses. Creating and deleting branches stay in the terminal. Then one Sync button carrying the ahead and behind counts and `mail-send-receive-symbolic`, then Commit. It pulls and then pushes, both halves every time, because nothing in the app fetches on its own and a behind count is therefore only as fresh as the last sync; a failed pull stops there and keeps its transcript. Where the branch has no upstream it is insensitive and says so, rather than answering every click with git's own "There is no tracking information". There is no Refresh button: a save, a watcher event and a `.git` write each schedule one already — a *write*, never a read, because inotify reports an open as well and the pane reading `.git/HEAD` used to come back as news for the pane, which asked git again about once a second for as long as the window was open — and the single refresh nobody can schedule for us is the one after `git init` in a vault that had no repository at all, which is what the Check Again button on the No Repository page is for. Commit rides in that row rather than on a line of its own: the two are the pane's actions, and a row of its own cost 40 px of a column that also has to hold the changes and the history. Then the commit message box, which takes `Ctrl+Return` while the keyboard is in it — the same chord is Insert Line Below, and an application accelerator is dispatched ahead of any controller on the focused widget, so `win.newline-below` offers it to the box first and inserts a line only where the box does not want it. It commits what is staged, or `git commit -a` where nothing is — tracked changes go in and an untracked file stays untracked, which is what a commit with an empty index means in VS Code. The box is one line at rest and grows with what is written into it, capped at eight lines and scrolling past that, because a commit message is a subject, a blank line and a body but must not push the changes and the history off the pane; its text sits 9 px inside its edges, which is what Adwaita gives an `entry`, so it has the same inset as the search field. Both the box and the button disappear when there is nothing to commit, but never while the box holds text or the keyboard: a refresh fires on every save, and one of those would otherwise take a half-written message with it. Below that a `GtkListView` of sections: Merge Conflicts, Staged Changes, Changes, Submodules. Empty sections are not drawn. A row's Stage / Unstage / Discard buttons appear on hover and on `:focus-within`, so the keyboard reaches what the pointer does; Discard is an `AdwAlertDialog`, being the one action here that can lose work. A single click on a row opens the diff as a tab, as one on a tree row opens the file. `Ctrl+Shift+G` shows the pane and puts the keyboard in the commit box, so a commit is written without reaching for the pointer. The lower half, across a vertical `GtkPaned` as in Tags, is the commit log: 200 at a time behind a Load More row, each with its lane drawn from `highlight::lane_colour` — the hue-rotation rule, this being the second thing after CSV columns that one accent cannot describe. Its rows expand on the same single click: a commit shows the files it changed, on the changes list's own letter/name/directory line, and one of those opens the commit against its first parent as a diff tab. One commit is expanded at a time, and a refresh closes it only where the history really moved: the page git has just read is compared against the page on screen, whole commits and not ids alone so that a branch moving onto one still redraws, and an identical page is not spliced at all. That is what leaves an expanded commit open across the save that scheduled the refresh, and leaves whatever Load More added below the first page alone. The store stays flat with two row kinds rather than becoming a `GtkTreeListModel` the refresh would have to keep in step |
| Editor | `sourceview5::View` inside an `AdwClampScrollable` inside a `GtkScrolledWindow`. The clamp is the scrollable one because that is what leaves the view as the scrolled window's own scrollable child: a plain `AdwClamp` is not a `GtkScrollable`, so GTK inserts a `GtkViewport`, the view's adjustments become throwaway ones nothing reads — every `scroll_to_mark`, GTK's own caret following included, writes to a dead adjustment — and `GtkViewport:scroll-to-focus` scrolls to the focused widget instead, which is what sent a scrolled note back to the top whenever a dialog took the focus and gave it back. Over the top of it, in the same overlay that carries the width probe, a sticky block title: the opening line of whatever the first visible line is inside, pinned there the way VS Code pins a function signature, and gone again once that line is back on screen. A block is a markdown heading or a fenced code block and nothing else — both are already tagged on the buffer by the styling pass, so the answer is a tag-toggle search through the buffer's own index rather than a second parse, and a language's own structure (a Python function, a LaTeX section) would need a parser this editor does not have. The innermost of the two wins, so a fence inside a section pins the fence. It is a plain label in the document font, aligned with the text column, on a `.view` box with a rule under it, and it never appears in a code or CSV tab |
| Code editor | the same `sourceview5::View`, told what it is by an `editor::Flavour` of `Note`, `Code` or `Csv`, so there is one tab type and not two. Code takes a GtkSourceView language guessed from the path and the content type, so `LICENSE` and `Makefile` open as what they are and not as plain text; it gets bracket matching, auto-indent, a four-space tab that stays a real tab where a makefile needs one, and the same wrapping prose gets: nothing in a document scrolls sideways, whatever language it is written in. `Alt+Z` unwraps one tab for as long as it is open, which is the escape hatch for the generated file whose columns really are the point. None of the markdown tags are installed on it. A CSV is code whose columns are coloured by the hue-rotation rule instead of by a language |
| Unreadable file | an `AdwStatusPage` in the tab itself, not a dialog and not a toast: `dialog-warning-symbolic`, a title of Binary File or File Too Large, the size in the body and a single Show in Files button. The tab keeps the warning icon, so the tab bar says which of the open files is the one that would not open |
| Preview | read-only WebKitGTK 6 view, same clamp width, stylesheet generated from `AdwStyleManager` |
| Terminal | a `vte4::Terminal` in a tab, not a panel: it lives in a pane's tab view, so it splits, drags between panes and windows, and takes the tab context menu with it. A shell at the bottom of the window is a pane split downwards, which is the same gesture that puts a note there. `Ctrl+J` opens one at the vault root, `$HOME` without a vault, and `Ctrl+W` closes it like any other tab — closing the tab ends the shell, because the widget is finalised and its pty hangs up, so nothing holds it strongly for longer than the tab lives. A focused shell keeps every chord the Keyboard table does not reserve, because a terminal that answers only half of readline is not a terminal. Colours are the resolved theme foreground *composited over* `theme::view_bg` — VTE keeps no alpha on a foreground, so libadwaita's 80 %-black light `view-fg-color` would otherwise paint pure black, darker than every other piece of text in the window — with VTE's own sixteen ANSI colours, the font is GNOME's monospace one scaled by the terminal's own zoom rather than by the document's, and the cursor is an underline so the character under it stays readable. It is inset 12 px either side off the spacing scale, not by the editor's 48 px page gutter: that is a measure for prose, and a terminal is a grid that should keep its columns. Opening one focuses the shell itself rather than the scroller around it, so it can be typed into without being clicked first. A secondary click opens a menu of its own: Copy and Paste, then New Terminal and Close Tab, then Open Link and Copy Link Address, the last pair only where there is a URL under the pointer. `http`, `https` and `mailto` URLs in the output are matched and drawn as links, OSC 8 hyperlinks included, and `Ctrl`-clicking one hands it to the desktop — plain clicking cannot, because VTE claims that press for its own selection. Those three schemes are an allowlist and not a filter: a shell's output is untrusted text, so a `file:` or `javascript:` URL it printed is neither drawn as a link nor launchable. `accent --terminal [PATH]` opens one in a vault-less window, at PATH, or `$HOME` — a path that is not a directory is reported and falls back rather than guessed at. That is accent as a terminal |
| Status bar | a `GtkBox` as the editor column's `AdwToolbarView` bottom bar, so presentation mode takes it away with the header and the find bar and the terminal panel stack above it. What the window is busy with at the start ("Indexing… 1200/42700 files", "Opening the document…") and the file's own facts at the end: what it is (`Markdown`, `PDF`, `Image`, or `<language> · UTF-8 · LF` for code), whether it has edits the disk does not, one count of its own, and how far it is zoomed. The count is one slot filled by whatever that tab has to count — a note's words, a code tab's errors and warnings, a PDF's `Page 4 of 12`, which follows the page under the middle of the viewport and so changes only when the page does. A note's count is re-read 300 ms after the last keystroke, on the same beat as the preview. The unsaved mark is the `•` a dirty tab already wears, so one symbol means the same thing in both places, and nothing at all is shown on a saved file. `.caption` `.dim-label`, 6 px padding, `accent-flat`. Every label hides when it has nothing to say. Two of its readouts are flat buttons — the branch, which syncs the repository the document sits in, and the zoom, which resets it — and `.accent-bar-button` pins both to the caption's own line height: Adwaita gives a button a 24 px minimum and 5 px of vertical padding, and a box is as tall as its tallest child however that child is aligned, so without the class either of them appearing lifted the whole bar from 29 px to 46 px. It reports the **active tab's** zoom or nothing at all — never the window's document zoom over a tab that zoom does not reach. The bar itself no longer answers a right-click with the window menu: an `AdwToolbarView` bottom bar is a `GtkWindowHandle`, and a footer of the document's own facts is not a title bar, so a secondary press anywhere in it is claimed and dropped. Button 1 is untouched, so the bar still drags the window. The whole bar carries `chrome-fade` and goes with the rest of the chrome while the user types, with no exception for the unsaved dot: a footer of facts about a document is not what anyone is reading mid-sentence. It speaks for the tab in front and for nothing else, so a window with no tab open shows no facts at all |
| View modes | Editor / Split / Preview; Split is a `GtkPaned` of the two above |
| Tabs | one `AdwTabView` + `AdwTabBar` per pane; panes nest in `GtkPaned`s. Each bar lives in the document column with the `.inline` style class rather than among the toolbar's top bars, so a bar spans its own pane and presentation mode takes it away with the document. A bar hides itself only while its pane is the only one and holds a single tab: with several panes the bar is what says which notes are where. A pane is split from the tab or tree context menu, from `win.split-*`, or by dropping a tab or a tree row on one of its four edges; a pane whose last note is closed or moved out closes with it, and the window always keeps one. A tab on a file from outside the window's vault carries `document-open-symbolic` as its indicator, tooltipped Outside this vault, so saving it is never a surprise and it is obvious why it has no backlinks. A tab dragged into **another window** moves there — the buffer is written out first, because a focus change always saves — and, one vault never having two windows, it always arrives from another vault: it is adopted as an absolute-path tab, the same model as a file opened from outside a vault, so it edits and saves but gets no index, backlinks or wikilink resolution. A terminal is a running shell and a diff is a view of two texts, so neither can be reopened elsewhere: those are handed back to their window with a toast. libadwaita detaches a dragged page from its view for the length of the drag and exposes no way to attach one, so the drop zones record where a drop landed and decline it, and `AdwTabView::create-window` — which that decline summons on the source view — is what hands the page its new home; a tab let go outside every window goes back where it came from. **Which tab is selected is decided by use, not by position.** Every pane keeps its own tabs in the order they were last selected: `Ctrl+Tab` steps one along that order and `Ctrl+Shift+Tab` the other way, and closing a tab falls back to the most recently used tab that is left rather than to the neighbour `AdwTabView` would pick. Per pane, because a pane owns its tab view and its bar is what says which notes are in it; a window-wide order would have to move the keyboard across a split, which is not what a split is for. The step is taken immediately and the order rewritten with it, so a second press forward comes back rather than going two tabs deep — VS Code's modal overlay, held while Ctrl is down and committed on release, is a lot of machinery for a chord whose common use is switching between the last two notes. Going back has no such limit: the least recently used tab is one step behind the front of a list that rotates, so repeated presses walk the whole history. The history needs no bookkeeping when a tab moves between panes or windows: it is pruned against the pane's own pages whenever it is read, so a tab that leaves drops out of one pane's order and joins the other's the moment it is selected there. **A tab opened by browsing is a preview** (VS Code's idiom): a click on a tree row, a search hit, a tag, a backlink, an outline heading or a Git changed file, and a wikilink followed. Each pane holds at most one, and the next such open closes it and takes its place, so clicking down a list of notes to see what is in them leaves one tab rather than twenty. Anything the reader named is kept — the palette, Open File…, a drop, a rename, the command line and the session, where the file was asked for by name. A preview becomes a real tab when it is edited, when its own tab is double-clicked, or when it is moved to another pane, all three being the reader saying they want to keep it; the session records no preview flag, so a restored tab is a real one. Nothing marks it in the bar: `AdwTabPage` has no style class and its title takes no markup, so VS Code's italic would need a tab widget of our own, while the icon slot says what the document is and the indicator slot says Outside this vault. A pane holding one tab hides its bar and so has no tab to double-click, which costs nothing: a preview alone in a pane is replaced in place, and editing it still keeps it |
| Palette | one `AdwDialog` with a `GtkSearchEntry` and a `GtkListView`; a leading `>` switches file mode to command mode (VS Code convention). Open Recent is the same dialog over the recent vaults, read the way the start screen reads them — a folder over its `~/…` path, a host over the path on that host — and it ends with Open Folder… and Open Remote…, the two ways to a vault the list does not hold. So one surface reaches every way of changing vault, and the list is never empty even in a window on the only vault known. The vault this window is already on is left out: picking it could only raise the window it was picked from |
| Find bar | one `GtkSearchBar` per window, a `GtkStack` of the find/replace row and the go-to-line row. It lives in the editor column's content rather than among the toolbar's top bars, because presentation mode unreveals those and hides the tab stack, and find has to survive both. The match readout says "3 of 12" over all three things it can search — the buffer, a PDF and the rendered preview. `WebKitFindController` reports a total and never a position, so the preview keeps the position itself: every fresh search drops the page selection first, which is what makes the first match reliably the first, and the two step actions walk the count the way WebKit walks the page. Past WebKit's 500-match ceiling the total is a floor and no position is claimed. Previous and next are `go-up-symbolic` and `go-down-symbolic`: the matches are places in a document that scrolls vertically, and back-and-forward arrows read as history. **Escape closes the bar wherever it is pressed** — the bar has a capture-phase controller of its own, ahead of `GtkSearchEntry`'s Escape, which would otherwise only clear the query, and the window carries a bubble-phase one for the Escape of somebody who typed a query and went back to reading. Bubble, so anything nearer the focus that answers to Escape still gets it first |
| Start screen | `AdwStatusPage` with app icon, Open Folder button and a recent-vaults list, shown when launched without a vault path and reachable again from Open Folder…, Open Remote…, Open Recent… and Close Vault in the primary menu. Only ever one of them: a second Open Folder… presents the one already up. Opening a vault gives it a window of its own, one per vault; Close Vault takes the current window away, which is what releases its vault, worker thread and WebKit process |
| Primary menu | four sections, grouped by what an item changes: the files in this vault (New Note, New Folder, Open File…, Save); which vault the window is on (Open Folder…, Open Remote…, Open Recent…, then Close Vault, the way out); what the window shows (Find, Toggle Split View, New Terminal, Presentation Mode); and the application (Preferences, About accent, Quit). Labels are never written at the menu — they come from the action table, so the menu and the palette cannot disagree |
| New Window | **One vault never has two windows** (VS Code's rule): a vault that already has a window raises it, whether the request came from the launcher, a second `accent <vault>` or the palette, because two windows over one index, session and watcher have no shared state to keep in step. New Window therefore opens the *start screen*, from which a vault without a window yet is picked. It is both an `app.new-window` GAction and a `new-window` desktop action, because GNOME Shell looks for either before it offers New Window in the launcher's context menu, and `accent --new-window` is how a second process asks for it |
| Window without a vault | a file named on the command line or handed over by the file manager — or `accent --terminal` — opens in a window that has no vault at all: no index, no watcher, tabs keyed by absolute path rather than by a vault-relative one, and nothing written to a session, because a window opened on one file is opened the same way again. Its sidebar holds the Outline pane alone, since the other five are views of an index; it starts hidden. One such window per process, so a second loose file joins it as a tab. Everything that needs the vault says so instead of failing quietly |
| Preferences | `AdwPreferencesDialog` with `AdwPreferencesPage` / `AdwPreferencesGroup` / `AdwSwitchRow`, plus an `AdwComboRow` for the theme and a destructive `AdwButtonRow` for Restore Defaults. The document font's Reset is an icon button (`document-revert-symbolic`, tooltipped): the row already carries a font button labelled with the whole font name, and a second text button beside it leaves the name nowhere to go |
| Tooltips | the full vault path with `$HOME` as `~` (`fileops::display_path`), on tree rows through `query-tooltip` and on tabs through `AdwTabPage:tooltip` |
| PDF | a `GtkScrollable` widget painting cached tiles, with a low-resolution stand-in under any page whose tiles have not arrived. One render thread per document, which also opens it, so a large file costs nothing at startup. Pages are recoloured onto the theme's own paper and ink (`theme::pdf_colours`) — light leaves them alone, dark and both Solarized halves remap them — and a drag selects the text under it, across a page break as readily as within one page: the glyphs of every page the drag covers, joined with a newline where it crosses. A secondary click over the page offers Copy and Copy Link to Selection while something is selected, then Export Highlights, then Pen and Eraser — `win.` actions in sections, the terminal's idiom, which is what puts them in the palette and lets them be rebound. **A highlight is a link**: Copy Link to Selection puts `[[paper.pdf#page=1&selection=0,6,0,15|the quoted text]]` on the clipboard, one per page the drag covered, and pasting it into any note is what makes the highlight — the index finds every link into this document, the four numbers become rectangles again against that page's glyphs, and they paint in the accent at alpha 0.2, under the selection and the search marks. Clicking one opens the note that holds it; following one from a note goes to the page and shows the selection. A link whose numbers no longer fit falls back to searching the text its alias quotes, and then to the page. Export Highlights writes them into the file as real `/Highlight` annotations in the accent, skipping quads the file already has. The drawing tools are a **ring**: three round buttons orbiting a hub, floating over the page, dragged anywhere in the pane by that hub and kept where this window last left them. The header's Drawing toggle opens and closes it, and shows only over a PDF. Pen draws `/Ink` at a uniform width in the accent; Highlighter draws the same annotation wide and translucent with a `Multiply` blend, so it darkens the text rather than covering it; Eraser takes a whole stroke within 4 pt of the pointer. A stroke stays painted over the page in its own tool's width and alpha until the re-rendered tile carries it. Both write the file itself, atomically and gated on the etag the document was read at; the tab knows its own write by that etag and does not reload over it. Insert Sketch puts a blank A4 page beside the note, embeds it and hands it the pen. The stand-ins are held to their own budget, a quarter of the tiles', so a long document scrolled end to end in the thumbnail strip does not keep every page it passed. Those colours are baked into a tile, so changing the theme drops every texture and renders the page again; the cache tells the two halves of light and dark apart on its own, but Adwaita and Solarized share a darkness and would otherwise keep each other's paper |
| Comparison | side-by-side line diff as a tab in the document area, keyed by what it compares rather than by a path, so asking twice reveals the tab already open. A sync conflict and a note that changed under its buffer carry a Keep Theirs / Keep Mine bar under the panes and the Mine pane is editable, so a conflict can be merged by hand before a side is kept; the alignment fillers are dropped again unless they were typed into. A git diff is the same widget with both panes read-only. It is a tab and not a dialog because a comparison is something to work beside, not an interruption to dismiss, and because git produces them by the dozen. Its panes are the one place a document does not wrap and does scroll sideways: the two share a single vertical adjustment and the alignment fillers assume one buffer line is one visual row, so a folded line would slide the two sides out of step |
| Language servers | one client for every text tab: accent's own index answers for markdown and a real server (clangd, rust-analyzer, pyright, taplo, …) is started on demand for code, so a note and a source file get the same surfaces from the same code path. **Completion** is `GtkSourceCompletion` with one provider — kind icon, label, the server's detail after it, its documentation in the details panel resolved when a row is looked at — and accepting a row applies the server's own edit, snippet tab stops and all, plus whatever import it brings, in one undo step. **Hover** is a `GtkSourceHoverProvider`: the server's markdown flattened to Pango markup, then every diagnostic covering that position, all four severities, because a hint says nothing on screen and this is where it is read. **Signature help** is a `GtkPopover` over the caret's line, the active parameter in bold; it never takes a grab, so the call it is about can go on being typed. **Diagnostics** underline the text, mark the gutter and print errors and warnings at the ends of their lines, and the status bar counts them where a note counts words. **Outline** and **References** are the two sidebar panes above, and **folding** is the gutter chevrons. A file whose server is not installed says so once — a toast on Go to Definition, a sentence in the Outline pane — and everything else about the tab goes on working. Which server answers for which language is a table in the app with a per-vault override in `config.toml` (`[vaults."<root>".lsp.servers]`); there is no preference for it, because the answer is either installed or it is not |
| Context menus | `GtkPopoverMenu` from a `gio::Menu`, parented to a layout-managed widget, grouped into sections: what creates or opens, what copies a path or leaves the app, then Move to Trash alone. Tree rows and tabs share the shape and the handlers. **New Note and New Folder are on every tree menu**, targeted at the folder that was clicked, the folder holding the file that was clicked, or the vault root — the blank area below the last row opens a menu of its own holding those two (and Upload Files… on a remote vault) and nothing else, because everything below them names a path. **Splitting is the tab menu's alone**: a split opens the active tab beside itself, which is not something done to a file in the tree. **There is no Move to…**: a row is moved by dragging it, and by typing a path into Rename, which is the same dialog either way and the keyboard's move. A popover parented by hand is unparented **from an idle**, never from `closed`: `closed` is emitted inside the item's own `clicked`, and an unparented widget cannot reach the action group it would have resolved through, so unparenting there silently drops the item's action |
| Empty states | `AdwStatusPage`: no vault, no note open, no search results, no backlinks on a note, no references on a source file, no language server for the open file, nothing to outline. The no-results copy is no longer note-shaped — "Nothing in this vault matches this search", because a hit can be a source file. `.compact` inside the sidebar, where the full size dwarfs a 200 to 420 px column |
| Feedback | `AdwToast` / `AdwBanner` / `AdwAlertDialog`, see States |
| Loading | the status bar's progress text; never a modal, never a blocked window. A background query whose answer replaces a list gets a `GtkProgressBar` across the top of that list instead, as the sidebar's search results have: it is faded rather than hidden, so nothing shifts when it comes and goes, and it is faded *in late* — a query that finishes inside the first 160 ms never draws it at all, because a bar that appears and goes in the same breath reads as a flash rather than as progress. The rule generalises to **a bar belongs to the surface it is about to fill**, which sanctions exactly one more of them: a remote vault's first connection, across the top of the document column. That wait is not a list being replaced, it is the whole column becoming usable, and it is seconds long because a first connection uploads the 6.4 MB server binary before anything else can happen. Elsewhere a 16 px `AdwSpinner` beside the control that started the work, except where beside it would move the layout: the status bar's branch readout is the Sync control and spins *over* its own name, the name faded rather than hidden so that it keeps its allocation, because a bar that changes width mid-sync is worse feedback than none |

## Typography

<https://developer.gnome.org/hig/guidelines/typography.html> · <https://developer.gnome.org/hig/guidelines/writing-style.html>

- Prose uses **Adwaita Mono at the GNOME document font's size** (`AdwStyleManager::document_font_name()`), applied to `textview.accent-doc` in `main.rs::install_document_font` and re-applied when the setting changes. Notes are prose, but a vault is prose with code fences, tables and wikilinks in it, and none of those line up in a proportional face, so the family is ours and only the size follows the system. One function writes both rules: `editor::font_css` builds the display-wide rule at zoom 1.0 and each tab's own rule at its zoom, so the family and the size are decided in one place and a zoomed note cannot come out in a different face from an unzoomed one. libadwaita 1.7 also exposes `--document-font-family` / `--document-font-size` as CSS variables, which is the upgrade path away from the hand-built provider.
- Code uses the GNOME **monospace** font from `StyleManager::monospace_font_name()`, named per view instead of through the display-wide rule that carries the document font to `textview.accent-doc`: one selector cannot answer for both, so a code view takes the `accent-code` class and a provider of its own. It sits in the same clamped, centred column as prose, with the same page gutters: a file is a document whichever language it is in, and a column that changes width from tab to tab is the thing the eye notices. Wrapping is on, as it is in prose: the far end of a long line is off the screen and out of the eye's way, which is worse than a folded line, so nothing inside a document scrolls sideways. `Alt+Z` unwraps a tab for as long as it is open; the scroller keeps a horizontal policy of `Automatic` rather than `Never` so that line stays reachable when it does, and because `Never` would make the scrolled window ask for the full width of the gutters. Line numbers are always shown. Its colours come from the GtkSourceView style scheme (`Adwaita` / `Adwaita-dark`, or `solarized-light` / `solarized-dark` under the Solarized theme), never from our own tags: `highlight.rs` installs nothing on a code buffer.
- **The syntax scheme is the one place the single-accent rule gives way**, and deliberately. One derived colour can say *this is a link*; it cannot say *keyword*, *string*, *comment* and *number* at the same time, and a dozen categories at once is what a scheme is for. Taking the platform's scheme answers light, dark and the user's own choice of theme in one move, and leaves no palette of ours to keep in step with GNOME's. Prose keeps the rule: a note is still styled from the accent and the foreground alone.
- Monospace appears only inside the `code`, `codeblock`, `math`, `html` and `frontmatter` text tags of a note.
- Heading scale in `highlight.rs`, relative to the document font: h1 1.6, h2 1.4, h3 1.2, h4 1.1; h5 and h6 are bold at 1.0. `strong` and list markers are weight 700, `em` is italic.
- Line numbers are optional and off by default in prose (`Config::line_numbers`, a switch in preferences); a code tab has them whatever the switch says, because code is read by line number and a compiler error names one. They are drawn by a `GtkSourceGutterRenderer` outside the 48 px page gutter, so turning them on shifts the page right rather than crowding it. Every line is numbered, headings included: the number and the hanging `#` markers are a whole gutter apart and read as two margins rather than as two things in one place. They rest at 0.6 opacity and come back to the style scheme's own gutter grey while the pointer is in the gutter — the whole column at once, not the line under the pointer. A gutter renderer has no colour property, so the dimming is the widget's opacity, which over the view's background is the same thing as the foreground at an alpha; the hover is an `EventControllerMotion` on the gutter, whose `contains-pointer` covers the renderer GTK actually picks. The gutter's *background* is the view's and not the scheme's: a style scheme may give `line-numbers` a background a shade off its own text background, as both Solarized halves do (`base2` on `base3`, `base02` on `base03`), which puts the numbers in a stripe beside the page against the one-flat-background rule. `textview border gutter` takes `var(--view-bg-color)` from the app's own display provider, which outranks the scheme's widget-level one.
- An ATX heading's `#` markers hang in the left gutter so its text lands on the body column, as in Apostrophe. `highlight.rs::hang` measures each level's markers in the view's own font at that level's scale and weight, then splits the width between the tag's `left-margin` and a negative `indent`; Pango reads that as a hanging indent, so wrapped heading lines stay on the body column too. A setext heading has no markers to hang. The markers of h5 and h6 are wider than the 48 px gutter and clamp at the window edge.
- A wrapped line carries on under its own gutter rather than under the left margin: a folded list item lines up with the text of its first line, and so does an indented continuation line with no marker at all. The same negative `indent`, with the left margin left alone so only the wrapped rows move. `typing::wrap_column` measures the gutter — the indent, plus a bullet, enumeration or quote marker and the space behind it — and `highlight::hang` turns the column into pixels with the font's own character advance. Twelve columns are tagged (`wrap1`..`wrap12`) and a deeper indent hangs at the twelfth: a tag's indent is a number of pixels and cannot be a function of the line it lands on. A task item hangs under its `[`, that being the line's first character. Markdown only; a code tab wraps flat, having no styling pass to hang off.
- Markup is styled as it is typed, not after a pause, for notes below 16 KB. Above that a full pass outlasts a frame, so it waits for the 150 ms debounce; the cost is dominated by re-tagging the buffer rather than by parsing it.
- Line length is set by width, not by counting characters. The editor wraps its view in an `AdwClampScrollable` whose `maximum-size` is a share of the editor's own width (`Config::column_width`), floored at 480 px, scaled by the document zoom, and followed by a `tightening-threshold` of three quarters of it — the 600 of 800 the fixed clamp had, so a window too narrow for the cap still gives the text everything it has. That width is the scroller's own allocation and not the horizontal adjustment's page size, which with the view as the scrollable child is the width of the column itself and would feed the cap back into itself until it collapsed onto the floor. GTK 4 has no signal for a widget's width — `::size-allocate` is gone and there is no width property — so a zero-sized `GtkDrawingArea` laid over the scroller reports it through `::resize`, which fires on every allocation and so covers the window, the paned handle, the sidebar, a split and the minimap in one hook. The preview caps its column at `56ch` (measured at 71 characters in Adwaita Sans, 62 in Cantarell). Measure rather than assume: `ch` is the width of a zero and much wider than an average letter.
- **The column's width is the user's dial**, Column Width in preferences: a percentage of the editor's own allocation, not the window's, since the sidebar and the preview take their share. 60 to 72 characters is where typography research puts comfortable prose, and the clamp was 580 to match it before the user asked for a document column of at least half the viewport. It is now exactly that. The default of 50 % is measured rather than picked: on the 1920 px screen this was written on, a maximised window leaves ~1640 px of editor, and half of it is 820 px — the fixed 800 px cap it replaces, to within a character. Who sees a change: a wider monitor, where the column now grows with the screen instead of holding a fixed ribbon in the middle, and a small window, where the old cap never applied at all and the text filled the width. The 480 px floor is what keeps that case readable at ~52 characters; it only ever applies below 1600 px of editor, because the row's minimum is 30 %. Zoom multiplies the cap along with the gutters, so a zoomed page keeps its proportions until the cap outgrows the editor and the column simply fills it.
- Header capitalisation for buttons, menu items, tab titles and tooltips; sentence capitalisation for messages and descriptions. Ellipsis (…) only when the label needs further input before acting. No OK / Yes / No buttons: label the affirmative button with its verb, for example Save or Discard.

## Colour

<https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.7/css-variables.html> · <https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.7/style-classes.html>. libadwaita's old `named-colors.html` page is gone (it 404s) and CSS variables replaced it, so `@named_color` syntax is out.

- The only three colour sources in code are `StyleManager::accent_color_rgba()`, `Widget::color()` (the resolved theme foreground) and `StyleManager::is_dark()`. A rendered PDF page is the exception that proves it: pixels cannot read a CSS variable, so `theme.rs` hands the renderer the paper and ink to map onto, and it is still the only file that writes a colour down.
- GTK CSS uses `var(--accent-bg-color)`, `var(--view-bg-color)`, `var(--window-fg-color)` and friends. Never `@named_colors`, never a literal hex.
- Editor tag colours, all derived, in `highlight.rs::restyle`: `link`, `wikilink`, `tag` and `image` take the accent at full alpha; `marker`, `frontmatter` and `listmarker` take the foreground at alpha 0.4; `quote` and `taskdone` the foreground at alpha 0.6; `code` and `codeblock` get a foreground background at alpha 0.07. 23 tags in total; no other colour is set anywhere.
- Two things depart from the single accent, both where one colour cannot carry the information. The first is the style scheme a code tab is coloured by, which Typography argues for. The second is a hue-rotated palette: a CSV's columns and the git log's lanes. `highlight.rs::restyle_csv` puts the accent through `gtk::rgb_to_hsv`, steps the hue a sixth of the wheel per column and converts back, so the six `csv0`..`csv5` tags keep the accent's saturation and value and column 0 is the accent itself; a seventh column repeats the first hue rather than inventing a colour. Derived at runtime like everything else, so it follows the system accent and writes no literal: `theme.rs` stays the only file with one.
- The preview stylesheet derives everything from three values: foreground, background, accent. WebKitGTK cannot see GTK's CSS variables, so it is handed the background as a literal, from `theme::view_bg`. One rule in it is not derived from those three: a `$$` block gets `margin: 1.2em 0`, the same standing room a heading takes above itself. A `<math display="block">` box is its own ink and carries none of the half-leading `line-height: 1.6` gives a line of prose, so without it two formulas sit closer together than two paragraphs and two in one paragraph touch. Measured under Xvfb at 11 pt: 12 px between the formulas and 0 px between two in one paragraph before, 18 px in both cases after, against 19 px of visual gap between two paragraphs; identical in light and dark, and 26 px at 16 pt, because the rule is in `em` and depends on no font's metrics.
- **`theme.rs` is the only file allowed to write a hex literal**, and anything outside it is a bug the pre-flight grep catches. It holds libadwaita's own `--view-bg-color` pair (`#ffffff` / `#1d1d20`) for the preview, and the Solarized palette: `#fdf6e3` / `#eee8d5` / `#657b83` light, `#002b36` / `#073642` / `#839496` dark.
- One flat background. The sidebar, both header bars, the tab bar and the document all paint `var(--view-bg-color)` through the `accent-flat` class, so the window reads as one surface rather than banded panels. The 1 px paned separator is the only division; it takes the accent colour under the pointer, keeping its width, thickens to 3 px while it is being dragged, and a double-click on it puts it back at its default position. Hover has to override the `box-shadow` Adwaita draws the line with rather than set a background: on a 1 px handle that inset shadow covers the whole allocation.
- Four themes: System, Light, Dark and Solarized, chosen in preferences. The first three are `AdwStyleManager` colour schemes and paint nothing of ours. Solarized redeclares libadwaita's `--*-bg-color` / `--*-fg-color` variables on `:root` from an app-priority provider, so every widget follows without being touched, and it keeps following the system between its light and dark halves. It deliberately leaves accent, shade and border variables alone, so the one-accent rule holds in all four.
- Light/dark parity is by construction: outside `theme.rs` nothing is picked per theme, so there is no second palette to keep in sync. Same for the accent, which the user can change at any moment.

## Spacing

The scale is 6, 12, 18, 24, 36 and nothing between: 6 inside a control group, 12 between related widgets, 18 between groups, 24 for dialog and page padding, 36 for empty-state breathing room. (The current HIG has no spacing page; this is the long-standing GNOME convention.) Current values: window 1100x760; sidebar floor 200, dragged on the paned handle and remembered in the session; editor margins left 48, right 48, top 24, bottom 96, with 2 px above and below lines (`main.rs`, `editor.rs`), all four scaled by the document zoom along with the clamp, so a zoomed page keeps its proportions and its character count instead of squeezing more text between unchanged gutters. A vertical `GtkSizeGroup` across the two header bars keeps both columns on one rhythm whatever the interface font, since the switcher rides in the sidebar header and the tree starts where the tab bar does. One CSS correction goes with it: libadwaita pads a header differently when it is the only bar in its `AdwToolbarView` than when it shares the area, which put the pane icons 3 px high, so `.accent-lone-header` cancels the difference. Every icon button in a header, the pane switcher included, is `Align::Center` rather than filling: a button stretched to the band's height comes out 34 by 40, and these read as square 34 by 34. The editor margins sit off the scale on purpose: they are page gutters inside the clamp, not layout spacing.

## Chrome auto-hide

The point of the app. Header bar, tab bar and status bar fade out while the user types and come back the moment attention leaves the text, in every view mode.

- Hides: the header bar, the tab bar and the status bar. Trigger: the first keystroke into the editor buffer.
- Returns on pointer motion anywhere in the window, Escape, focus change, a view-mode change, an action fired from the palette or a menu, and any keyboard focus move out of the editor. Hover must never be the only route back, or a keyboard-only user is stuck with hidden chrome.
- Never hides: the editor, toasts, banners, dialogs. The sidebar's panes dim to 50 % instead of hiding, on the same transition: the tree is where the reader is in the vault, so it recedes rather than disappearing. The pane switcher does fade to nothing, and deliberately so: it rides in the sidebar header, so it goes with the rest of the top band and the two columns stay in step. Suspended entirely while a dialog, banner, popover, the palette or the find bar is open.
- Implementation: a CSS `opacity` transition on a `.chrome-hidden` class. Opacity only, so the layout never shifts and the widgets keep their size and focus order. `AdwToolbarView:reveal-top-bars` is the named upgrade path if the CSS approach ever fights the toolbar view (<https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.7/class.ToolbarView.html>).
- With `gtk-enable-animations` false the class still toggles but the transition is zero-length, so chrome jumps instead of fading and nothing becomes unreachable (<https://docs.gtk.org/gtk4/property.Settings.gtk-enable-animations.html>).

| Window | Fullscreen `F11`, Preferences `Ctrl+comma`, Primary menu `F10` |
| Tabs and panes | Next / Previous Tab `Ctrl+Tab` / `Ctrl+Shift+Tab`, `Ctrl+PageUp` / `Ctrl+PageDown`, `Alt+1` to `Alt+9`; Split Right `Ctrl+\`, the other three sides from the menus and the palette. The first pair are ours and walk the pane's tabs in **most recently used** order (see the Tabs row of the layout map); the rest stay `AdwTabView`'s own, because stepping along the bar and picking a tab by number are exactly what it already means by them. `AdwTabView:shortcuts` gives up the two Tab chords in exchange, and `Ctrl+Home` / `Ctrl+End` with them: libadwaita binds those to first and last tab, which took two GtkSourceView built-ins the never-bind list below reserves, so `Ctrl+Home` in a note left the note instead of going to its start. Next and Previous Tab are in the terminal's reserved set for the same reason Close Tab is — a tab chord has to mean the same thing over every tab, and they were `AdwTabView`'s capture-phase chords before they were actions, so a shell never had them to lose |

Never bind: `Super`+anything (the shell owns it), `Alt+Tab`, `Alt+F4`, `Alt+F7`, `Alt+F8`, `Ctrl+Alt+*` (workspace switching), `F1` (help), `Ctrl+Shift+U` (IBus unicode entry), `Ctrl+Space` (input-method switch), and the GtkSourceView built-ins (`Ctrl+Z`/`Ctrl+Y`, `Ctrl+A`, `Ctrl+X`/`C`/`V`, `Alt+Up`/`Alt+Down`, `Ctrl+Home`/`Ctrl+End`).

The table is the set of defaults, not a fixed fact. The accelerator beside a command in the palette is a button: clicking it asks for a new chord, Backspace unbinds the command and Restore Default puts the table's chord back. Overrides are stored in the `[shortcuts]` table of `~/.config/accent/config.toml`, keyed by full action name (`"win.save" = ["<Control>s"]`), and only what the user changed is written, so the table above keeps deciding everything else; an empty list means deliberately unbound, and an unbound action still lists in the palette, so nothing becomes unreachable. A chord already in use is refused by naming the command that holds it, and a clash introduced by hand-editing the file is marked on both rows. The never-bind list is shown in the rebind dialog rather than enforced: the desktop and the widget keep those chords whatever we store.

Five of the Editing chords are already spoken for by the widget: GtkTextView binds `Ctrl+Up`/`Ctrl+Down` to paragraph movement and `Ctrl+K` to deleting to the end of the line, and GtkSourceView binds `Shift+Alt+Up`/`Shift+Alt+Down` to `move-viewport`. All are class shortcuts, which run at the focused view before the window's application accelerators, so `install_actions` claims them in a capture-phase `GtkShortcutController` on the window that forwards them to the same actions. Taking a widget binding needs that much deliberation; it is not the default way to add a shortcut. It runs the other way for a controller one of our own widgets adds: the accelerator is dispatched first and the controller never sees the key, so a chord a focused widget of ours has to own is handed to it by the action instead — which is how the git commit box keeps `Ctrl+Return`.

One deliberate HIG deviation: the HIG reserves `Ctrl+P` for Print and `Ctrl+Shift+P` for Print Preview. accent has no printing, and its users arrive from VS Code and Obsidian where both open the palette. Revisit if printing is ever added.

The view control is a single toggle button, not a group: two states need one button, and the icon names the state it is in (a pencil in Editor, split panes in Split) on top of the pressed styling. It matches `Ctrl+M`. Preview is not a third state: `F5` is presentation mode, which hides the sidebar, the tab bars and both header bars and shows the note rendered. A tab that draws its own document — a PDF, an image, a diff, a terminal — is presented as it is instead: there is nothing for the preview to render, so the document column stays and only the tab bars go with the chrome. A PDF also fits a whole page while it lasts and takes its zoom back on the way out. It deliberately does not resize the window; fullscreen stays `F11`'s job, so the two compose. The bars go through `AdwToolbarView::set_reveal_top_bars(false)` rather than the opacity fade, because a fade leaves an empty band where a presentation needs the whole window, and the pointer-motion reveal is suppressed while it is on. It is deliberately not saved in the session: restoring into a chromeless window would be hard to leave.

There is no shortcuts window. `AdwShortcutsDialog` needs libadwaita 1.8 and we build against 1.7; `GtkShortcutsWindow` is deprecated since GTK 4.18 and will be removed in GTK 5. Until the libadwaita floor moves to 1.8 the palette's command mode is the shortcuts reference, so it must show the accelerator next to every command.

## Iconography

Symbolic icons from the Adwaita theme, with one shipped set as the exception (the completion kinds, below): no other bundled glyphs, no emoji (<https://developer.gnome.org/hig/guidelines/ui-icons.html>). All of the following were confirmed present in `/usr/share/icons/Adwaita/symbolic/` on the development machine (adwaita-icon-theme 50):

`sidebar-show-symbolic`, `open-menu-symbolic`, `document-new-symbolic`, `folder-new-symbolic`, `document-save-symbolic`, `document-edit-symbolic`, `document-open-recent-symbolic`, `document-revert-symbolic`, `edit-find-symbolic`, `edit-find-replace-symbolic`, `system-search-symbolic`, `edit-clear-symbolic`, `view-dual-symbolic`, `view-reveal-symbolic`, `view-fullscreen-symbolic`, `view-refresh-symbolic`, `user-bookmarks-symbolic`, `mail-reply-sender-symbolic`, `x-office-calendar-symbolic`, `user-trash-symbolic`, `folder-symbolic`, `text-x-generic-symbolic`, `x-office-document-symbolic`, `window-close-symbolic`, `preferences-system-symbolic`, `dialog-warning-symbolic`, `dialog-error-symbolic`, `object-select-symbolic`, `go-previous-symbolic`, `go-next-symbolic`, `list-add-symbolic`, `view-list-bullet-symbolic`, `document-open-symbolic`, `mail-send-receive-symbolic`, `go-down-symbolic`, `go-up-symbolic`, `list-remove-symbolic`, `view-dual-symbolic`.

This theme has no `tag-symbolic`, so the Tags pane uses `user-bookmarks-symbolic`. It has no git, branch or history glyph either, so the Git pane, its Sync button and its No Repository page all use `mail-send-receive-symbolic`, arrows leaving and arriving, which is what the pane's one network action is. They used `network-transmit-receive-symbolic`, and that name turned out to be the rule below in practice: Adwaita draws it as two arrows, WhiteSur as a boxed device, and the Git tab read as a network port. Same reading, a name whose artwork is arrows in both themes. Backlinks uses `mail-reply-sender-symbolic`, an arrow turning back, for "what points here": the theme's only link-named glyph, `insert-link-symbolic`, is a text-insertion mark and sits 2 units high on its own canvas, which is visible as an off-centre icon in a switcher. Outline uses `view-list-bullet-symbolic`, a list of indented lines, which is what the pane is. A tab on a file from outside the vault is marked with `document-open-symbolic`, the icon of the action that put it there. If a glyph is missing: take the closest existing Adwaita name first, and only if nothing fits ship one in the app `GResource` under the `io.github.stroblme.Accent` prefix, drawn on the 16 px symbolic grid with `fill="currentColor"` so it recolours with the theme. Never ship a coloured icon.

Diagnostics use `dialog-error-symbolic` and `dialog-warning-symbolic` in the line-mark gutter, which is the pair every desktop already reads as those two severities; a fold's chevron is `go-down-symbolic` open and `go-next-symbolic` shut, the same two the sidebar's disclosures use. The one shipped set is the completion kinds: Adwaita has no glyph for a function, an enum member or a type parameter, so eighteen `lsp-<kind>-symbolic` icons live in the app `GResource` at `/io/github/stroblme/Accent/icons/scalable/actions/` and are found by name like any other icon, `IconTheme::add_resource_path` having been pointed at the prefix at startup. They are [tabler-icons](https://github.com/tabler/tabler-icons) outlines (MIT, `apps/gtk/data/icons/LICENSE.tabler`) with their strokes converted to fills on the 16 px grid, because GTK recolours a symbolic icon by its `fill`. The drawing ring's three, `tool-pen`, `tool-highlighter` and `tool-eraser`, go through the same pipeline but are drawn for accent: the theme has no pen, marker or eraser at all, and the header's Drawing toggle uses `document-edit-symbolic`, the pencil, which it does have. A GResource rather than hicolor so that a run from the source tree has them too, and the same pipeline is what any further shipped glyph goes through.

**The name is ours, the artwork is not.** An icon theme may replace any Adwaita name, and what it ships may not render: the Replace toggle used `pan-down-symbolic` and was invisible for a user on WhiteSur, whose copy of that file is the one in the theme written with single-quoted attributes (`fill='#363636'`), which GTK4's symbolic recolouring does not parse. The button drew nothing, with no warning on the console. So prefer a name that says what the control does over one that says which way a panel opens: `edit-find-replace-symbolic` is worth more than a chevron even before the bug, and a generic shape is the easiest thing for a theme to have redrawn. `pan-down-symbolic` was the only name we used that WhiteSur ships in the broken form, and nothing uses it now.

## States

- Empty: `AdwStatusPage` with a symbolic icon, a header-capitalised title, one sentence of body text and at most one button (<https://developer.gnome.org/hig/patterns/feedback/placeholders.html>). In the sidebar add `.compact`, or the icon alone takes 128 px of a 200 px column.
- A context menu never scrolls. GTK re-presents a popover only when its parent is allocated, and a widget with a custom `size_allocate` such as `GtkListView` never does, so a menu hung off one freezes at its first-frame size and `GtkPopoverMenu`'s inner scrolled window turns the difference into a scrollbar. Parent it to a plain box instead, and translate the pointer position into that box's coordinates.
- Loading: the status bar's progress text, as `start_reconcile` already does ("Indexing… 1200/42700 files"). Indexing and saving never block the window, so no spinner covers content and no progress bar owns the window. Two bars are drawn, and no third without a line in this file. The first is the sidebar's search progress, a thin pulse above the results while a query is on its worker thread; it belongs to the list it is about to replace, not to the window, and it is held back for the first two pulses so that a query nobody asked for — the requery a changed file triggers under a finished search — is over before there is anything to see. The second is a remote vault's first connection (`connect.rs`), across the top of the document column, which is the surface that wait is about to make usable: determinate while the server binary uploads, because that step knows how far it has got, and pulsed through the steps that do not. GTK4 has no indeterminate mode, so both pulses are a timer of ours, and every one of them is removed when the work ends and when its widget's window closes — a leaked `glib::timeout` keeps firing.
- Toast for a thing that happened and is over ("Saved", "Moved to Trash" with an Undo button). Banner for a state that persists and needs a decision ("This note changed on disk", "A sync conflict copy of this note exists"). A conflict raises the banner on the tab showing the note it concerns, never a toast per conflict copy in the vault: on a synced vault that was a wall of them at startup. Conflicts on notes nobody has open are counted on the end of the "Indexed N files" toast instead. The same rule covers the vault worker's own failures — indexing, link resolution, watching — which are index maintenance nobody can act on and which recur for as long as their cause does: each distinct one is said once per vault and logged every time (`Worker::fail`), because an autosave that failed to index raises the same toast on the next keystroke, and the next. `AdwAlertDialog` only when the choice can lose data: overwrite, discard, delete permanently. <https://developer.gnome.org/hig/patterns/feedback/toasts.html> · <https://developer.gnome.org/hig/patterns/feedback/banners.html> · <https://developer.gnome.org/hig/patterns/feedback/dialogs.html>
- A file that will not open as text raises neither a dialog nor a toast: its tab holds an `AdwStatusPage` instead, for a binary file (a NUL byte in the bytes, the same test `grep` and `git` use) and for anything over the 16 MiB `fs::MAX_TEXT` cap. The file is what failed, so the failure belongs in that file's own tab and stays there until the tab is closed, rather than in a message that has to be dismissed before the window is usable again.
- A file that is text but not valid UTF-8 opens read-only behind a banner with no button. What is on screen is a lossy reading of the bytes, so the only safe answer is to leave the file alone, which is what the tab already does; a banner is a state that persists, and not every state has an answer to offer.
- A tab has one banner and can have more than one thing to say about its file, so the questions queue rather than overwrite each other, and the bar shows the one that can cost most: "deleted on disk", then "changed on disk", then a sync conflict copy (which blocks nothing), then the read-only report (which asks nothing). Taking one down brings the next back up instead of clearing the bar — a conflict copy appearing used to wipe the "changed on disk" question, and resolving that copy then took the bar away with the wiped question still standing, leaving a tab that would never autosave again and nothing on screen to say why. Queued and not merged: `AdwBanner` has exactly one button, and two questions on one line have no honest single label.
- **Saving never answers a question.** A buffer whose file moved underneath it holds the only copy of both its edits and the answer the user has not given, so nothing writes until they give it — VS Code's rule, and `editor::may_save` is the one predicate every save path asks. Autosave becomes a plain no-op, with the banner and the tab's dot as the only signal: it cannot raise a modal on every focus change and idle second, and it deliberately does not write the buffer anywhere else either, because a copy nothing in the app ever reads back is a second source of truth. Ctrl+S refuses too, and says so with the overwrite dialog (or, over a note deleted on disk, by writing it back, which is what that banner's button already offers). The two paths a tab leaves by are the exception: a tab closing and a window closing still attempt the write and ask when it is refused, because a buffer on its way out has nowhere else to be kept and refusing there would lose it outright. Underneath all of it the etag gate in `fs::write_note` has the last word, and a failed `stat` is never read as a change — "I could not find out" is not "someone else wrote this".

## Motion

libadwaita defaults only: no custom easing, no staggered reveals, nothing that animates on load. The only timings we own are debounces, and they exist to keep the main loop free.

The document follows the caret and nothing else. The view is the scrolled window's scrollable child, so GTK keeps the insert mark on screen by itself — arrow keys, typing, find, Go to Line, a search hit and every extra caret land in view without anyone asking. Nothing else moves the viewport: a wheel scroll away from the caret stays where it was put, and a dialog opening and closing over it puts nothing back.

## Pre-flight checklist

Ten mechanical checks before shipping a UI change. None of them needs judgement.

1. `cargo fmt --all --check`
2. `cargo clippy -p accent --all-targets --locked -- -D warnings`
3. `cargo test --locked && cargo test -p accent --locked`
4. Headless smoke run: `make smoke` (its `XVFB_ENV` carries `GDK_BACKEND=x11` and `GTK_A11Y=none` as well as `G_DEBUG=fatal-criticals`; see ROADMAP §6 for why each is load-bearing)
5. Dark: `gsettings set org.gnome.desktop.interface color-scheme prefer-dark`, look, then set it back to `default`
6. Accent: `gsettings set org.gnome.desktop.interface accent-color teal`, look, then set it back to `blue`
7. No stray colours: `grep -rnE '#[0-9a-fA-F]{3,8}' apps/gtk/src | grep -v theme.rs` returns nothing
8. Reduced motion: `gsettings set org.gnome.desktop.interface enable-animations false`, check nothing became unreachable, then set it back to `true`
9. Keyboard-only pass with the pointer unplugged: reach every action in the accelerator table, and get the auto-hidden chrome back without a mouse
10. `GDK_SCALE=2 target/release/accent testvault` for scaling, plus an IME check (ibus, type CJK into a note and confirm the preedit lands in the right place)
