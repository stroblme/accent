# accent design guidelines

These rules cover the GTK4 + libadwaita desktop app, which is what exists today; each section also carries a Material 3 note so the Phase 3 Compose app starts from the same decisions instead of a second design pass. The precedents are Apostrophe and GNOME Text Editor: the note fills the window, the chrome stays out of the way, nothing is decorative. Where this document is silent the GNOME Human Interface Guidelines decide (<https://developer.gnome.org/hig/>, <https://developer.gnome.org/hig/principles.html>). Every URL below was checked and resolves.

## Principles

1. The note is the UI. Everything else is scaffolding that earns its pixels or disappears.
2. One accent colour, taken from the system. No second brand colour, no decorative chrome.
3. Every action is reachable from the keyboard, and the palette is the discoverable index of them.
4. Light and dark are the same design, not two designs. Same for the seven system accents.
5. The system owns fonts, colours, animation and scaling. We only own layout and behaviour.

## Layout map

| Surface | Widget |
|---|---|
| Window shell | `AdwApplicationWindow` > `GtkPaned`, one `AdwToolbarView` per side, each with its own `AdwHeaderBar` |
| Header bars | two, so the sidebar reaches the top of the window and the tab bar spans only the editor column. Sidebar header: the start window controls, and otherwise empty. Main header: the sidebar toggle (always visible, so a collapsed sidebar can be brought back without the keyboard), `AdwWindowTitle` with vault name and note path, the Drawing toggle where the view-mode toggle used to be and only while a PDF or a diagram is in front — with Undo and Redo to its left while a tool is in hand and either has something to walk (over a diagram, whenever either has: every edit there is a step), as a pair so neither moves under the pointer, the one with nothing insensitive —, primary menu, end window controls. Toggle Preview keeps its action, its chord and its place in the primary menu; what it lost is the button, a window having only so many places for one. What the window is busy with and what the file is went to the status bar: a header carries the document's name, not its facts. The main header takes over the start window controls when the sidebar is hidden. The *window's* own title — what the switcher and the task manager show, the one place windows have to be told apart — is the vault name alone, `Notes (host)` on a remote one and `Accent` with no vault, and it does not follow the open tab: that is what the header bar is for |
| Sidebar | `AdwInlineViewSwitcher` in icon mode over an `AdwViewStack` of eight equal panes: Files, Search, Tags, References, Git, Ports, Outline, Properties. Git shows itself only where there is a repository to talk about, so a vault that is not under version control keeps the switcher it had, Ports only on a remote vault, the one kind with an ssh connection to forward over, and Properties only while a diagram is in front — the one document with properties to set. **Properties** is the diagram's own widget: groups of `AdwPreferencesGroup` rows for the selected cells (Shape: fill and line colour, each a `gtk::ColorDialogButton` beside a switch for having one at all, line width, dashed, rounded, shadow, opacity; Text: size, colour, bold/italic/underline, alignment; Line, for an edge: route and both arrow heads; Style: the raw style string, one cell's, applied on Enter) and, with nothing selected, the page (name, background, size). Every row is one undo step, and spin rows wait for a burst of steps to settle. A colour dialog cannot be given a palette, so none is imitated: GTK's own chooser, which remembers the colours picked in it, is the whole picker. The pane leaves by showing Outline first, so the stack never shows nothing; its icon is `document-properties-symbolic`. **Ports** lists the forwards running over that connection, a row each — `8080 → 80`, the local port on the left either way round, a tooltip naming both ends and a button that stops it — above two port boxes with the direction between them as a flat button that flips it: `→` is a port on this machine reaching the remote one (`ssh -L`), `←` a port on the remote machine reaching this one (`ssh -R`, which the host binds to its loopback). The direction is kept across Adds, and a row's own is read-only: a forward the other way round is a new forward, not an edit. ssh refusing a port is a banner over the list, since it is the state of a forward that is not up. The connection keeps the list and puts it back after a reconnect; nothing outlives the vault. **A vault always opens on Files**, whichever pane was showing when it was last closed: coming back to a search someone ran in another sitting is not where a vault starts. The switcher is the title widget of the sidebar's header bar, so the pane icons sit on the same line as the sidebar toggle and the mode group, and the tree's first row lines up with the tabs. Width is dragged on the `GtkPaned` handle, floor 200. The vault's own name sits above the tree as a plain label with a folder icon: it is what the listing is *of*, so there is nothing to open or expand, and it is the one root drop zone that is still on screen when the tree is scrolled too deep to have any blank area left. **Files lists every folder in the vault**, the ones the index deliberately does not walk included — `node_modules`, `__pycache__`, a `.venv`, a cargo `target/` — because a listing that silently leaves a folder out is one nobody can trust. Those rows are read straight off the disk, one level per expansion (`walk::unindexed_children`), and nothing else changes: the trees stay out of the index, the watcher and every query, so a 40 000-file `node_modules` costs nothing until someone opens the row. They are dimmed by the same rule the git-ignored rows are and for the same reason — search does not reach them. What may be done to one depends on **why** the index does not hold it (`walk::Unindexed`): a **dependency tree** — `node_modules`, a `.venv`, a marked `target/` — is somebody else's, so it lists and opens but is never changed (no context menu, no marking, no drag out, no drop in), while a folder the reader **gitignored** — an `mlruns/`, a build output — is their own and gets the whole menu like any other row. Being out of the index stops a file being searched, not edited. Nothing in the vault's watch set reports a write into either, so a **gitignored folder carries a `GFileMonitor` of its own** for as long as the tree holds its listing (`tree::watch_unindexed`, local vaults only): a build writing into an open row shows up the way anything else does. A dependency tree gets none — 40 000 files is the tree this must not watch — and is still only as fresh as its last expansion. `.git` and `.trash` are out of reach here as everywhere. The merge happens where the files are (`Vault::list_dir`), so a vault on another machine gets it too. **Dot-named files and folders are listed too, dimmed** — `.gitignore`, `.python-version`, `.obsidian` — because a vault holds dotfiles people edit, and dimmed because they are still what a file manager calls hidden. Show Hidden Files, on by default, is the switch: a check item ending every tree menu and a palette command, with no chord because `Ctrl+H` is Replace. Off, it leaves out every dot-named path the index holds; the skipped trees above still list, `.venv` included, as they did before there was a switch. It is a preference, so every window follows it. **The selection follows the open tab**, so the highlight says which file is in front rather than which row the pointer last crossed — GTK's single-click-activate also means *selected on hover*, and the two are one mechanism, so the open file's row is put back the moment the pointer leaves the list. Only among the rows already on screen: a shut folder is not opened and the list is not scrolled, which is what Reveal in Sidebar is for. **Ctrl+click and Shift+click mark rows**, which is the tree's only multiple selection: an explicit set of its own rather than the selection, that one being the hover highlight and the open file at once, and a marked row is tinted with the accent. Shift+click marks every row on screen from the last one clicked without Shift to the one clicked and replaces the marks, Shift+Ctrl+click adds the range to them; a shut folder in the range is marked whole, so opening it shows everything in it marked, and a Ctrl+click on one of those takes that one alone out of the set. Neither click opens a file or toggles a folder, a plain click and Escape let the set go — on a marked row once the press has turned out to be a click rather than a drag — and a row the index does not hold is never marked. A right-click on a marked row is about the whole set, so the menu offers Cut, Copy, Move to Trash, Paste and Show Hidden Files and nothing that names one file (Principle 1); a right-click anywhere else forgets the marks and gets the ordinary menu. Delete trashes the set, and a marked row dragged carries it; whatever acts on the set acts on its top-most paths, a marked folder taking what is inside it, and any move or trash lets the marks go, since it may have taken what they named. There is no keyboard multi-select. **Files is a drag surface both ways**: a row dragged into a pane opens the note there and one dragged onto a pane's edge splits it, while a row dragged back into the tree moves the file — onto a folder into that folder, onto a file beside that file, onto the vault label or the blank area below the last row into the vault root, which is the same target that row's New File would have used. Directories drag too. The two drags carry two content types: the plain string a pane opens, and a `GtkStringObject` only the tree's targets take, so a folder — which offers the second alone — can never be dropped into a pane and opened as a note. A marked row carries the whole set as a `GtkStringList`, which the tree alone takes too, and the set lands as one move: one plan, one Update Links? question, and a name the destination already holds refuses all of it. A move that cannot happen is refused while the pointer is still over the row, which simply does not light up: a folder onto itself, a folder into something under it, and anything into the folder it is already in. GTK's own `:drop(active)` outline is the whole of the feedback, and there is no insertion line. What is left goes through the same plan-and-rewrite Rename does, so open tabs follow the file and the links keep their confirmation. **Files from another application land too**: a drag from GNOME Files offers a `GdkFileList`, which the same three zones take and which copies the files into that folder through `fileops::import` — the path a paste of the file manager's clipboard already takes, so a name that is taken gets the same `(copy)` mark and a remote vault gets the same upload. A drop that offers move alone, which is Shift held in the file manager, moves instead. A drag of either kind that comes to rest over a shut folder opens it after a second, so a file reaches a folder that was not on screen when the drag began; nothing shuts it again. Search carries the entry on a line of its own, a row holding a `.linked` group of Match Case / Match Whole Word / Regular Expression / All toggles with the replace toggle at its far end, a revealer holding the replace field, and a progress bar between the controls and the results; the four toggles are text buttons (`Aa`, `Word`, `.*`, `All`) because Adwaita has no glyph for any of them, while the replace toggle is an icon because `edit-find-replace-symbolic` names exactly what it reveals. It sits outside the `.linked` group: the four change what the query means, it opens a panel. The search space by default is everything the index holds — every note plus every other text file under 1 MiB — minus what git ignores; `All` drops that exclusion in either mode, and reaches the trees the walk never entered (`node_modules`, a `.venv`, a `target/`) **in an exact search only** — the exclusion is a column, which the ranked query reads as well, while the skipped trees are a walk, and only the exact path makes it, at the cost of that walk per query. Its tooltip names both halves rather than promising the second one everywhere; forcing exact mode instead would turn a two-word ranked query into a literal-substring one, so asking for more files would quietly find fewer. Replace All rewrites every file the index holds a body for — a source file as much as a note — so the number on the button is every match the index lists, uncapped: the button counts what it will write. The rows All's walk adds past the index are listed without the replacement preview, because the rewrite never opens those files. `.git` and `.trash` are out of reach even then. **A note is never excluded, whatever ignores it**: a notes vault that gitignores its own `*.md` is the ordinary case, so every one of these filters carries an explicit markdown escape, and the file tree lists an ignored file dimmed rather than hiding it. There is no ignore file inside the vault: `.accentignore` was removed, and what a user wants left out is named in one place instead, `[search] exclude` in `config.toml` — a list of vault-relative directory paths that joins git's own answer in the same exclusion column, so it obeys every rule above, `All` still reaches it, the tree still dims it, a note inside it is still found, and a vault with no repository has an exclusion mechanism again. It does not replace `walk.rs`'s built-in skips, which are about what the index and the kernel's watch budget can hold rather than about what a reader wants to see. Tags splits its column on a second vertical `GtkPaned`, tag list above, the files carrying the selected tag in the lower third. References answers one question for every kind of file: on a note it lists the notes that link to it, once each, because a note that links three times is one backlink; on a source file it lists every place the symbol under the caret is used, `path:line`, and follows the caret while the pane is on screen. Wherever that would be nothing — a PDF, an image, a diagram, a text file no language server answers for, or the caret on nothing the server knows — it lists the notes that link to the file instead, the way a note's backlinks are listed. Outline is an `AdwBin` rather than a list of its own, because what belongs in it is the open tab's business: the symbols the language layer names for the open file — a note's headings, a source file's functions and types, nested as the server nests them — the PDF viewer's bookmarks and thumbnails — the strip also where its pages are moved, inserted and deleted (see PDF) — and an empty state when there is nothing to outline. **On a text tab it follows the caret**, as VS Code's Follow Cursor does: the row of the innermost heading or symbol whose range holds the caret is selected — none above the first heading, or between two functions — and scrolled into view as little as it takes, never activated and never given the keyboard. Above the first heading the list goes back to its top, so it never shows a part of the file the caret is not in; a gap between two functions leaves it where it is, or it would jump to the top and back as the caret crossed one. An edit refills the list in place and a tab switched back to opens on its caret's section rather than at the top. The rows are in the file's order, so a caret move costs a bisection, not a walk; while the pane is out of sight it costs nothing, and showing the pane catches up. The selection is GTK's hover highlight too, so the caret's row is put back when the pointer leaves the list, as the file tree puts back the open file's. There is no toggle. Its rows activate on a single click, and so does every other result list here — search hits, the files under a tag, the backlinks — as the file tree's rows and the Git pane's changed files already did: one click opens what a row stands for, which is how GNOME's own sidebars behave. What a click opens is the pane's **preview** tab, so walking a list of results replaces one tab instead of leaving twenty behind; a double-click on the tab, or the first edit, keeps it. **A result row is a match, not a file**, in either search: a note saying the query five times is five rows, each quoting the line it sits on with the match marked in it and naming the file and that line in dim beside it, and one file may fill five rows before the rest are gathered into a "+N more in this file" row under them, so no one file takes the list. A hit that names a place in the file — every hit of either search does now, save a note found by its title alone, which quotes the head of the note — opens on that place and leaves the match marked. **The marks are the tab's**, not the bar's: switching to another tab and back shows the note still marked, and they last until an edit moves them or that pane's bar replaces or clears the query |
| Git pane | one repository at a time, chosen in a `GtkDropDown` that hides itself when there is only one and whose button ellipsizes the name, a repository being named after its directory and that name otherwise deciding how narrow the whole sidebar can be dragged. Under it a branch row: the branch itself, on a `GtkMenuButton` whose label is the branch HEAD is on — or `Detached at abc1234` where it is on no branch at all, which is the same string the status bar shows. Its popover is a scrolled `GtkListBox` of the repository's local branches, then under a small dim Remote heading the remote-tracking branches no local branch shares a name with, with Create Branch… and Merge Branch… buttons under them, so the readout is also every branch operation the pane offers. Picking a row is `git switch`, and whether that is safe is git's call: its own first line comes back as a toast and the label goes back to the branch HEAD is really on where it refuses. Picking a remote row is `git switch --track`, which makes the local branch git names after it, tracking it, and switches to it; `origin/x` with a local `x` already there is not listed, being that row already. Each row but the checked-out one carries a trash button, on hover as the changed files' actions are, because git refuses to delete the branch HEAD is on and a control that cannot work is dead chrome. Deleting runs `git branch -d` and escalates to `-D` only where git itself says the branch is not fully merged, which is an `AdwAlertDialog` naming what would be lost — the one refusal here worth a second question, and no guess of ours at what a default branch is. Delete Branch… in the palette is the same delete for the keyboard: a dropdown of the other local branches in an alert whose Delete is destructive, then the trash button's path. Creating is `git switch -c`: from HEAD, no base picker, the name validated by git rather than by a pattern of ours. A remote row carries no trash button: deleting a branch on the remote is a push, and stays a terminal job. Merging is `git merge` of one of the other local branches into HEAD, picked from a dropdown in a dialog named after the branch it lands on: no fast-forward flag, so git's default and the user's own `merge.ff` decide, and whether the working tree allows it is git's call too. The toast says what came of it — already up to date, fast-forwarded, merged, or conflicts in N files — read off the repository rather than off git's words. A merge that stopped raises an `AdwBanner` over the whole pane, "A merge is in progress", until the merge is committed or aborted; its Abort asks first, `git merge --abort` taking every resolution made so far with it. A rebase that stopped — a pull under `pull.rebase` most often — raises the same banner reading "A rebase is in progress", and there Commit reads Continue and the message box goes, each commit keeping its own message: `git rebase --continue` where the conflicts are staged, `git rebase --abort` behind the same question. A Continue that stops on the next commit's conflicts leaves the banner where it is. The conflicts are the Merge Conflicts section's: a row opens the note with git's markers in it, Stage marks it resolved, and nothing opens on its own. Then one Sync button carrying the ahead and behind counts and `mail-send-receive-symbolic`, then Commit. It pulls and then pushes, both halves every time: the counts are kept current by a background fetch of the selected repository — on opening the vault, on picking a repository, and every five minutes while the window has the focus — but they are a readout rather than a decision and can be a whole interval old; a failed pull stops there and keeps its transcript. That fetch interrupts nobody when it fails, and says so on the Sync tooltip instead. It and a Sync never run together, since both write the remote-tracking refs and git refuses the second with `cannot lock ref`: the fetch skips a tick that lands on a Sync, and a Sync asked for mid-fetch waits for it, 8 s at most. Where the branch has no upstream the button stays live and its tooltip says Publish: syncing pushes the branch to its remote (the only one, or `origin`) and tracks it, rather than answering every click with git's own "There is no tracking information". There is no Refresh button: a save, a watcher event and a `.git` write each schedule one already — a *write*, never a read, because inotify reports an open as well and the pane reading `.git/HEAD` used to come back as news for the pane, which asked git again about once a second for as long as the window was open — and a `git init` in a vault that had no repository at all is such a write like any other, so the pane answers that one by going looking for repositories and shows itself the moment it finds one, with nothing to click and no walk to wait for. Commit rides in that row rather than on a line of its own: the two are the pane's actions, and a row of its own cost 40 px of a column that also has to hold the changes and the history. Then the commit message box, which takes `Ctrl+Return` while the keyboard is in it — the same chord is Insert Line Below, and an application accelerator is dispatched ahead of any controller on the focused widget, so `win.newline-below` offers it to the box first and inserts a line only where the box does not want it. It commits what is staged, or `git commit -a` where nothing is — tracked changes go in and an untracked file stays untracked, which is what a commit with an empty index means in VS Code. Never during a merge, where `-a` would stage the unresolved files with their markers: the box reads Merge message (optional) instead, Commit is live with nothing staged, and an empty box commits git's own message with its `# Conflicts:` list stripped. What Commit waits for is the conflicts: while any of them is still unstaged it is insensitive, tooltipped Stage the resolved conflicts first, and `Ctrl+Return` in the box does nothing, because git would only refuse the commit. The box is one line at rest and grows with what is written into it, capped at eight lines and scrolling past that, because a commit message is a subject, a blank line and a body but must not push the changes and the history off the pane; its text sits 9 px inside its edges, which is what Adwaita gives an `entry`, so it has the same inset as the search field. Both the box and the button disappear when there is nothing to commit, but never while the box holds text or the keyboard: a refresh fires on every save, and one of those would otherwise take a half-written message with it. Below that a `GtkListView` of sections: Merge Conflicts, Staged Changes, Changes, Submodules. Empty sections are not drawn. Each section's files are **grouped by folder** by default: folders before files at every level, both sorted as the file tree sorts them, a chain of folders with a single child each compressed onto one row (`src/deep`, as VS Code does it), and a folder row folding away what is under it. A flat list of thirty changes repeats the same directory thirty times, which is what the grouping is for; under a folder row the file's own dimmed directory label goes, being on screen already. Every file row of the folder view clears the chevron column, a file at the repository root included, so its icon sits under a sibling folder's. It is one preference, `git_tree` in `config.toml`, set by one switch in Preferences: how a list is shaped is not a per-window state, and the header it used to ride is the narrowest strip in the sidebar. Both redraw from the last refresh's answers, so neither costs a `git status`. A row's Stage / Unstage / Discard buttons appear on hover and on `:focus-within`, so the keyboard reaches what the pointer does, while the focus a click leaves on a row keeps them no longer than the pointer stays; Discard is an `AdwAlertDialog`, being the one action here that can lose work. A folder row of the tree view offers the same buttons for everything under it in its section, and none in Merge Conflicts, where a conflict is resolved one file at a time; its Discard names how many files go back to the index and how many untracked ones go to the trash, all in one go. A single click on a row opens the diff as a tab, as one on a tree row opens the file; a file deleted from the working tree has no file for that tab to hold, so it opens as the index against nothing, a transient tab like a staged change's. A row names a path and does not hold what git said about it: where the file has been staged, discarded or committed since the last refresh — from the pane, from a terminal, or across a click the list was held still for — the working tree and the index carry the same text, and a comparison of two identical columns is not an answer, so the pane says the file has no unstaged changes and asks git again, which takes the row with it. `Ctrl+Shift+G` shows the pane and puts the keyboard in the commit box, so a commit is written without reaching for the pointer. The lower half, across a vertical `GtkPaned` as in Tags, is the commit log: 200 at a time behind a Load More row, each with its lane drawn from `highlight::lane_colour` — the hue-rotation rule, this being the second thing after CSV columns that one accent cannot describe. Its rows expand on the same single click: a commit shows the files it changed, on the changes list's own letter/name/directory line, and one of those opens the commit against its first parent as a diff tab. Each row leads its summary with a small label per decoration — HEAD's branch in the accent colour, a remote branch dimmer, a tag outlined, three at most and a `+N` for the rest — read with `--decorate=full`, so a branch and a tag of one name stay apart; `origin/HEAD`, the stash and notes are not decorations a row speaks for. `git::lanes` names each lane after the first decorated commit on it and hands the name down its first parents, and a commit where other named lanes end says "side branched here" under its author line. That is the graph's own reading and no git call of its own, so a branch that has not diverged from the one below it — a feature branch ahead of main — shares one lane with it and forks nowhere. A commit row carries Check Out Commit and Copy Commit ID, on the row's hover and `:focus-within` and in the same revealer the changed files' actions use, so the summary has the whole width of the pane until the pointer or the keyboard is on it: two things are two buttons and not a menu. The checkout is `git switch --detach` and asks nothing first, git refusing it where uncommitted work would be lost exactly as it refuses a branch switch. Moving onto a branch that is on the commit belongs to the branch popover, which lists every branch there is and switches or tracks it; the row's own decorations say which of them are here. Hovering a commit shows the decorations pointing at it, its short id, the lane it is on ("On main") and the whole message, all of it from the `%D` and `%b` the log already fetched rather than a query per hover. One commit is expanded at a time, and a refresh closes it only where the history really moved: the page git has just read is compared against the page on screen, whole commits and not ids alone so that a branch moving onto one still redraws, and an identical page is not spliced at all. That is what leaves an expanded commit open across the save that scheduled the refresh, and leaves whatever Load More added below the first page alone. The store stays flat with two row kinds rather than becoming a `GtkTreeListModel` the refresh would have to keep in step |
| Editor | `sourceview5::View` inside an `AdwClampScrollable` inside a `GtkScrolledWindow`. The clamp is the scrollable one because that is what leaves the view as the scrolled window's own scrollable child: a plain `AdwClamp` is not a `GtkScrollable`, so GTK inserts a `GtkViewport`, the view's adjustments become throwaway ones nothing reads — every `scroll_to_mark`, GTK's own caret following included, writes to a dead adjustment — and `GtkViewport:scroll-to-focus` scrolls to the focused widget instead, which is what sent a scrolled note back to the top whenever a dialog took the focus and gave it back. Over the top of it, in the same overlay that carries the width probe, a sticky block title: the opening line of whatever the first visible line is inside, pinned there the way VS Code pins a function signature, and gone again once that line is back on screen. A block is a markdown heading or a fenced code block and nothing else — both are already tagged on the buffer by the styling pass, so the answer is a tag-toggle search through the buffer's own index rather than a second parse, and a language's own structure (a Python function, a LaTeX section) would need a parser this editor does not have. The innermost of the two wins, so a fence inside a section pins the fence. It is a plain label in the document font, aligned with the text column, on a `.view` box with a rule under it, and it never appears in a code or CSV tab |
| Code editor | the same `sourceview5::View`, told what it is by an `editor::Flavour` of `Note`, `Code` or `Csv`, so there is one tab type and not two. Code takes a GtkSourceView language guessed from the path and the content type, so `LICENSE` and `Makefile` open as what they are and not as plain text; it gets bracket matching, auto-indent, a four-space tab that stays a real tab where a makefile needs one, and the same wrapping prose gets: nothing in a document scrolls sideways, whatever language it is written in. `Alt+Z` unwraps one tab for as long as it is open, which is the escape hatch for the generated file whose columns really are the point. None of the markdown tags are installed on it. A CSV is code whose columns are coloured by the hue-rotation rule instead of by a language |
| Unreadable file | an `AdwStatusPage` in the tab itself, not a dialog and not a toast: `dialog-warning-symbolic`, a title of Binary File or File Too Large, the size in the body and a single Show in Files button — Download… on a remote vault, where no file manager here can reach the file. The tab keeps the warning icon, so the tab bar says which of the open files is the one that would not open |
| Preview | read-only WebKitGTK 6 view, same clamp width, stylesheet generated from `AdwStyleManager` |
| Terminal | a `vte4::Terminal` in a tab, not a panel: it lives in a pane's tab view, so it splits, drags between panes and windows, and takes the tab context menu with it. A shell at the bottom of the window is a pane split downwards, which is the same gesture that puts a note there. `Ctrl+J` opens one at the vault root, `$HOME` without a vault, and `Ctrl+W` closes it like any other tab. Every shell is held by `accent-cli hold`, one daemon per user and machine that owns the pty, the process and a `vt100` model of the screen; what runs in the tab's own pty is `accent-cli attach <id>`, a client that only relays bytes one way and keystrokes and sizes the other — dtach's shape, and the same command over `ssh -t` on a host. So Close Tab ends the shell (`accent-cli kill`), closing the window only lets go of it, and a vault or a terminal session opened again attaches to the same shell, its history and screen replayed. The tab key is `terminal:<16 hex>`, the id the daemon holds it under; where the shell is (OSC 7, else where it started) goes into the session, so one the daemon lost — a reboot — starts again there. Without `accent-cli` beside `accent` the tab runs `$SHELL` as it used to and says so once per window; an `attach` that fails on its own account exits 254 and its tab stays, so the line it printed can be read. A remote vault's root that is not on the host still gets a shell, at the login's home, so a window opened at a mistyped path is never without one (the holder falls back without a word of it, which NOTEPAD records). ## Typography

<https://developer.gnome.org/hig/guidelines/typography.html> · <https://developer.gnome.org/hig/guidelines/writing-style.html>

- Prose uses **Adwaita Mono at the GNOME document font's size** (`AdwStyleManager::document_font_name()`), applied to `textview.accent-doc` in `main.rs::install_document_font` and re-applied when the setting changes. Notes are prose, but a vault is prose with code fences, tables and wikilinks in it, and none of those line up in a proportional face, so the family is ours and only the size follows the system. One function writes both rules: `editor::font_css` builds the display-wide rule at zoom 1.0 and each tab's own rule at its zoom, so the family and the size are decided in one place and a zoomed note cannot come out in a different face from an unzoomed one. libadwaita 1.7 also exposes `--document-font-family` / `--document-font-size` as CSS variables, which is the upgrade path away from the hand-built provider.
- Code uses the GNOME **monospace** font from `StyleManager::monospace_font_name()`, named per view instead of through the display-wide rule that carries the document font to `textview.accent-doc`: one selector cannot answer for both, so a code view takes the `accent-code` class and a provider of its own. It sits in the same clamped, centred column as prose, with the same page gutters: a file is a document whichever language it is in, and a column that changes width from tab to tab is the thing the eye notices. Wrapping is on, as it is in prose: the far end of a long line is off the screen and out of the eye's way, which is worse than a folded line, so nothing inside a document scrolls sideways. `Alt+Z` unwraps a tab for as long as it is open; the scroller keeps a horizontal policy of `Automatic` rather than `Never` so that line stays reachable when it does, and because `Never` would make the scrolled window ask for the full width of the gutters. Line numbers are always shown. Its colours come from the GtkSourceView style scheme (`Adwaita` / `Adwaita-dark`, or `solarized-light` / `solarized-dark` under the Solarized theme), never from our own tags: `highlight.rs` installs nothing on a code buffer.
- **The syntax scheme is the one place the single-accent rule gives way**, and deliberately. One derived colour can say *this is a link*; it cannot say *keyword*, *string*, *comment* and *number* at the same time, and a dozen categories at once is what a scheme is for. Taking the platform's scheme answers light, dark and the user's own choice of theme in one move, and leaves no palette of ours to keep in step with GNOME's. Prose keeps the rule: a note is still styled from the accent and the foreground alone.
- Monospace appears only inside the `code`, `codeblock`, `math`, `html` and `frontmatter` text tags of a note.
- Heading scale in `highlight.rs`, relative to the document font: h1 1.6, h2 1.4, h3 1.2, h4 1.1; h5 and h6 are bold at 1.0. `strong` and list markers are weight 700, `em` is italic.
- Line numbers are optional and off by default in prose (`Config::line_numbers`, a switch in preferences); a code tab has them whatever the switch says, because code is read by line number and a compiler error names one. They are drawn by a `GtkSourceGutterRenderer` outside the 48 px page gutter, so turning them on shifts the page right rather than crowding it. Every line is numbered, headings included: the number and the hanging `#` markers are a whole gutter apart and read as two margins rather than as two things in one place. They rest at 0.6 opacity and come back to the style scheme's own gutter grey while the pointer is in the gutter — the whole column at once, not the line under the pointer. A gutter renderer has no colour property, so the dimming is the widget's opacity, which over the view's background is the same thing as the foreground at an alpha; the hover is an `EventControllerMotion` on the gutter, whose `contains-pointer` covers the renderer GTK actually picks. The gutter's *background* is the view's and not the scheme's: a style scheme may give `line-numbers` a background a shade off its own text background, as both Solarized halves do (`base2` on `base3`, `base02` on `base03`), which puts the numbers in a stripe beside the page against the one-flat-background rule. `textview border gutter` takes `var(--view-bg-color)` from the app's own display provider, which outranks the scheme's widget-level one.
- An ATX heading's `#` markers hang in the left gutter so its text lands on the body column, as in Apostrophe. `highlight.rs::hang` measures each level's markers in the view's own font at that level's scale and weight, then splits the width between the tag's `left-margin` and a negative `indent`; Pango reads that as a hanging indent, so wrapped heading lines stay on the body column too. A setext heading has no markers to hang. The markers of h5 and h6 are wider than the 48 px gutter and clamp at the window edge.
- A wrapped line carries on under its own gutter rather than under the left margin: a folded list item lines up with the text of its first line, and so does an indented continuation line with no marker at all. The same negative `indent`, with the left margin left alone so only the wrapped rows move. `typing::wrap_column` measures the gutter — the indent, plus a bullet, enumeration or quote marker and the space behind it — and `highlight::hang` turns the column into pixels with the font's own character advance. Twelve columns are tagged (`wrap1`..`wrap12`) and a deeper indent hangs at the twelfth: a tag's indent is a number of pixels and cannot be a function of the line it lands on. A task item hangs under its `[`, that being the line's first character. Markdown only; a code tab wraps flat, having no styling pass to hang off.
- Markup is styled as it is typed, not after a pause, for notes below 16 KB. Above that a full pass outlasts a frame, so it waits for the 150 ms debounce; the cost is dominated by re-tagging the buffer rather than by parsing it.
- Line length is set by width, not by counting characters. The editor wraps its view in an `AdwClampScrollable` whose `maximum-size` is a share of the editor's own width (`Config::column_width`), floored at 480 px, scaled by the document zoom, and followed by a `tightening-threshold` of three quarters of it — the 600 of 800 the fixed clamp had, so a window too narrow for the cap still gives the text everything it has. That width is the scroller's own allocation and not the horizontal adjustment's page size, which with the view as the scrollable child is the width of the column itself and would feed the cap back into itself until it collapsed onto the floor. GTK 4 has no signal for a widget's width — `::size-allocate` is gone and there is no width property — so a zero-sized `GtkDrawingArea` laid over the scroller reports it through `::resize`, which fires on every allocation and so covers the window, the paned handle, the sidebar, a split and the minimap in one hook. The preview caps its column at `56ch` (measured at 71 characters in Adwaita Sans, 62 in Cantarell). Measure rather than assume: `ch` is the width of a zero and much wider than an average letter.
- **The column's width is the user's dial**, Column Width in preferences: a percentage of the editor's own allocation, not the window's, since the sidebar and the preview take their share. 60 to 72 characters is where typography research puts comfortable prose, and the clamp was 580 to match it before the user asked for a document column of at least half the viewport. It is now exactly that. The default of 50 % is measured rather than picked: on the 1920 px screen this was written on, a maximised window leaves ~1640 px of editor, and half of it is 820 px — the fixed 800 px cap it replaces, to within a character. Who sees a change: a wider monitor, where the column now grows with the screen instead of holding a fixed ribbon in the middle, and a small window, where the old cap never applied at all and the text filled the width. The 480 px floor is what keeps that case readable at ~52 characters; it only ever applies below 1600 px of editor, because the row's minimum is 30 %. Zoom multiplies the cap along with the gutters, so a zoomed page keeps its proportions until the cap outgrows the editor and the column simply fills it.
- Header capitalisation for buttons, menu items, tab titles and tooltips; sentence capitalisation for messages and descriptions. Ellipsis (…) only when the label needs further input before acting. No OK / Yes / No buttons: label the affirmative button with its verb, for example Save or Discard.

## Colour

<https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.7/css-variables.html> · <https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.7/style-classes.html>. libadwaita's old `named-colors.html` page is gone (it 404s) and CSS variables replaced it, so `@named_color` syntax is out.

- The only three colour sources in code are `StyleManager::accent_color_rgba()`, `Widget::color()` (the resolved theme foreground) and `StyleManager::is_dark()`. A rendered PDF page is the exception that proves it: pixels cannot read a CSS variable, so `theme.rs` hands the renderer the paper and ink to map onto, and it is still the only file that writes a colour down.
- GTK CSS uses `var(--accent-bg-color)`, `var(--view-bg-color)`, `var(--window-fg-color)` and friends. Never `@named_colors`, never a literal hex.
- Editor tag colours, all derived, in `highlight.rs::restyle`: `link`, `wikilink`, `tag` and `image` take the accent at full alpha; `marker`, `frontmatter` and `listmarker` take the foreground at alpha 0.4; `quote` and `taskdone` the foreground at alpha 0.6; `code` and `codeblock` get a foreground background at alpha 0.07. 23 tags in total; no other colour is set anywhere.
- Two things depart from the single accent, both where one colour cannot carry the information. The first is the style scheme a code tab is coloured by, which Typography argues for. The second is a hue-rotated palette: a CSV's columns and the git log's lanes. `highlight.rs::restyle_csv` puts the accent through `gtk::rgb_to_hsv`, steps the hue a sixth of the wheel per column and converts back, so the six `csv0`..`csv5` tags keep the accent's saturation and value and column 0 is the accent itself; a seventh column repeats the first hue rather than inventing a colour. Derived at runtime like everything else, so it follows the system accent and writes no literal: `theme.rs` stays the only file with one.
- The preview stylesheet derives everything from three values: foreground, background, accent. WebKitGTK cannot see GTK's CSS variables, so it is handed the background as a literal, from `theme::view_bg`. One rule in it is not derived from those three: a `$$` block gets `margin: 1.2em 0`, the same standing room a heading takes above itself. A `<math display="block">` box is its own ink and carries none of the half-leading `line-height: 1.6` gives a line of prose, so without it two formulas sit closer together than two paragraphs and two in one paragraph touch. Measured under Xvfb at 11 pt: 12 px between the formulas and 0 px between two in one paragraph before, 18 px in both cases after, against 19 px of visual gap between two paragraphs; identical in light and dark, and 26 px at 16 pt, because the rule is in `em` and depends on no font's metrics.
- A diagram's page is the other thing painted in colours that are not ours: a draw.io file says what colour every shape, line and label is, and the canvas paints them as authored, in light and dark alike, the theme reaching only the surround and the accent only the selection. The Properties pane's colour dialog may put any colour into the document. None of it is a literal in code: a colour there is data read from the file.
- **`theme.rs` is the only file allowed to write a hex literal**, and anything outside it is a bug the pre-flight grep catches. It holds libadwaita's own `--view-bg-color` pair (`#ffffff` / `#1d1d20`) and the foregrounds that go on them, the Solarized palette (`#fdf6e3` / `#eee8d5` / `#657b83` light, `#002b36` / `#073642` / `#839496` dark, Ethan Schoonover's, MIT), and three sixteen-colour ANSI palettes for the terminal: Ayu and Ayu Light (Ivan Demchenko, MIT, transcribed from `mbadolato/iTerm2-Color-Schemes`) under the Adwaita themes, Solarized's own under Solarized. Only the dark one carries a contrast floor in the tests — 3.0:1 on `#1d1d20`, which VTE's built-in blue fails at 1.41 — because Ayu Light and Solarized are deliberately low-contrast designs and ship as their authors made them.
- One flat background. The sidebar, both header bars, the tab bar and the document all paint `var(--view-bg-color)` through the `accent-flat` class, so the window reads as one surface rather than banded panels. The 1 px paned separator is the only division; it takes the accent colour under the pointer, keeping its width, thickens to 3 px while it is being dragged, and a double-click on it puts it back at its default position. Hover has to override the `box-shadow` Adwaita draws the line with rather than set a background: on a 1 px handle that inset shadow covers the whole allocation.
- Four themes: System, Light, Dark and Solarized, chosen in preferences. The first three are `AdwStyleManager` colour schemes and paint nothing of ours. Solarized redeclares libadwaita's `--*-bg-color` / `--*-fg-color` variables on `:root` from an app-priority provider, so every widget follows without being touched, and it keeps following the system between its light and dark halves. It deliberately leaves accent, shade and border variables alone, so the one-accent rule holds in all four.
- Light/dark parity is by construction: outside `theme.rs` nothing is picked per theme, so there is no second palette to keep in sync. Same for the accent, which the user can change at any moment.

## Spacing

The scale is 6, 12, 18, 24, 36 and nothing between: 6 inside a control group, 12 between related widgets, 18 between groups, 24 for dialog and page padding, 36 for empty-state breathing room. (The current HIG has no spacing page; this is the long-standing GNOME convention.) Current values: window 1100x760; sidebar floor 200, dragged on the paned handle and remembered in the session; editor margins left 48, right 48, top 24, bottom 96, with 2 px above and below lines (`main.rs`, `editor.rs`), all four scaled by the document zoom along with the clamp, so a zoomed page keeps its proportions and its character count instead of squeezing more text between unchanged gutters. A vertical `GtkSizeGroup` across the two header bars keeps both columns on one rhythm whatever the interface font, since the switcher rides in the sidebar header and the tree starts where the tab bar does. One CSS correction goes with it: libadwaita pads a header differently when it is the only bar in its `AdwToolbarView` than when it shares the area, which put the pane icons 3 px high, so `.accent-lone-header` cancels the difference. Every icon button in a header, the pane switcher included, is `Align::Center` rather than filling: a button stretched to the band's height comes out 34 by 40, and these read as square 34 by 34. The editor margins sit off the scale on purpose: they are page gutters inside the clamp, not layout spacing.

## Chrome auto-hide

The point of the app. The chrome fades out while the user types and comes back the moment attention leaves the text, in every view mode. How much fades is the Focus Mode preference (`focus_mode` in `config.toml`): three levels in one combo row under Theme rather than a switch per surface, because each level contains the one before it.

- **None**: nothing fades.
- **Medium**, the default: the header bars, the tab bars, the status bar, the sidebar's panes and the minimap go to nothing. The panes used to dim to 50 % and stay, as the reader's place in the vault; they go with the rest now, the tree being one pointer move away. The pane switcher rides in the sidebar header and goes with the top band, so the two columns stay in step.
- **High**: Medium, plus every pane but the one being written in recedes to 0.3 (`.chrome-away` on the pane, so a PDF or a shell recedes like a note), the dividers go — every paned handle, and the undershoot line a scrolled window draws against a flat bar (`.dividers-hidden` on the window), which at full strength would frame the panes that recede — and the text in the focused view fades away from the carets, as in Apostrophe's focus mode. A line keeps `α(d) = F + (1 − F)·exp(−d²/2σ²)` of itself, `d` being its distance in buffer lines from the span the carets and the selection cover, with σ = 2 and F = 0.3 — the same floor the receding panes have, one constant (`fade::FLOOR`), and neither is a preference. The unit is the buffer line: a paragraph in prose, a line in code, and a markdown blank line between two paragraphs counts as one. The split preview stays crisp.
- Hides on the first keystroke into the editor buffer.
- Returns on pointer motion anywhere in the window, a wheel or touchpad scroll, Escape, focus change, a view-mode change, and any keyboard focus move out of the editor. Hover must never be the only route back, or a keyboard-only user is stuck with hidden chrome. The scroll is a capture-phase controller on the window that lets the event on to the scroller, because a touchpad scroll need not move the pointer and looking around the document is attention leaving the line. Firing an action is deliberately *not* a route back: a chord is typing, not attention leaving the text, so `Ctrl+S` and the scroll chords keep the mode. An action from the palette or a menu still reveals it, through those routes rather than through the activation — the palette is a focus change, a menu click is pointer motion. Coming back takes away everything a level faded, whatever the level is by then.
- Never hides: the editor, toasts, banners, dialogs, an open find bar. Suspended entirely while a dialog, banner, popover or the palette is open, but not while the find bar is: its matches are what the reader is working through, so at High a line holding one keeps all of itself however far it is from the caret (`fade::cover`), and the text between them recedes as usual.
- Implementation: a CSS `opacity` transition on the `.chrome-hidden` and `.chrome-away` classes. Opacity only, so the layout never shifts and the widgets keep their size and focus order. `AdwToolbarView:reveal-top-bars` is the named upgrade path if the CSS approach ever fights the toolbar view (<https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1.7/class.ToolbarView.html>).
- The line fade is not CSS and not text tags: `GtkTextTag` has no opacity, a `foreground-rgba` would flatten a note's link colours and a code tab's syntax colours into one grey, and re-tagging on every toggle is the tag churn a re-style is already dominated by. The view paints a band of its own background over each visible line in its `AboveText` layer instead, under the carets and the ghost text: the theme's view background over a note, the style scheme's `text` background over code and CSV. A band is as wide as the text window, so it takes the page gutters and the heading markers hanging in the left one, and stops at the line-number gutter, which is a window of its own. It ramps in and out over the chrome's own 250 ms and lives only while the chrome is hidden.
- With `gtk-enable-animations` false the classes still toggle but the transition is zero-length, and the line fade jumps with them, so nothing fades and nothing becomes unreachable (<https://docs.gtk.org/gtk4/property.Settings.gtk-enable-animations.html>).

Five of the Editing chords are already spoken for by the widget: GtkTextView binds `Ctrl+Up`/`Ctrl+Down` to paragraph movement and `Ctrl+K` to deleting to the end of the line, and GtkSourceView binds `Shift+Alt+Up`/`Shift+Alt+Down` to `move-viewport`. It runs the other way for a controller one of our own widgets adds: the accelerator is dispatched first and the controller never sees the key, so a chord a focused widget of ours has to own is handed to it by the action instead — which is how the git commit box keeps `Ctrl+Return`.

One deliberate HIG deviation: the HIG reserves `Ctrl+P` for Print and `Ctrl+Shift+P` for Print Preview. accent has no printing, and its users arrive from VS Code and Obsidian where both open the palette. Revisit if printing is ever added.

The view control is a single toggle button, not a group: two states need one button, and the icon names the state it is in (a pencil in Editor, split panes in Split) on top of the pressed styling. It matches `Ctrl+M`. Preview is not a third state: `F5` is presentation mode, which hides the sidebar, the tab bars and both header bars and shows the note rendered. A tab that draws its own document — a PDF, an image, a diff, a terminal — is presented as it is instead: there is nothing for the preview to render, so the document column stays and only the tab bars go with the chrome. A PDF also fits a whole page while it lasts and takes its zoom back on the way out. It deliberately does not resize the window; fullscreen stays `F11`'s job, so the two compose. The bars go through `AdwToolbarView::set_reveal_top_bars(false)` rather than the opacity fade, because a fade leaves an empty band where a presentation needs the whole window, and the pointer-motion reveal is suppressed while it is on. The status bar alone comes back while the pointer rests on the strip at the bottom of the document column where it sits, and goes when the pointer leaves that strip or the window: over the document rather than pushing it up (`extend-content-to-bottom-edge` while presenting), so nothing reflows under the pointer, and on a background that covers the whole bar, its spacing being padding rather than margins. It is deliberately not saved in the session: restoring into a chromeless window would be hard to leave.

There is no shortcuts window. `AdwShortcutsDialog` needs libadwaita 1.8 and we build against 1.7; `GtkShortcutsWindow` is deprecated since GTK 4.18 and will be removed in GTK 5. Until the libadwaita floor moves to 1.8 the palette's command mode is the shortcuts reference, so it must show the accelerator next to every command.

It has no git, branch or history glyph either, so the Git pane and its Sync button both use `mail-send-receive-symbolic`, arrows leaving and arriving, which is what the pane's one network action is. They used `network-transmit-receive-symbolic`, and that name turned out to be the rule below in practice: Adwaita draws it as two arrows, WhiteSur as a boxed device, and the Git tab read as a network port. Same reading, a name whose artwork is arrows in both themes. Backlinks uses `mail-reply-sender-symbolic`, an arrow turning back, for "what points here": the theme's only link-named glyph, `insert-link-symbolic`, is a text-insertion mark and sits 2 units high on its own canvas, which is visible as an off-centre icon in a switcher. Outline uses `view-list-bullet-symbolic`, a list of indented lines, which is what the pane is. A tab on a file from outside the vault is marked with `document-open-symbolic`, the icon of the action that put it there. If a glyph is missing: take the closest existing Adwaita name first, and only if nothing fits ship one in the app `GResource` under the `io.github.stroblme.Accent` prefix, drawn on the 16 px symbolic grid with `fill="currentColor"` so it recolours with the theme. Never ship a coloured icon.

Diagnostics use `dialog-error-symbolic` and `dialog-warning-symbolic` in the line-mark gutter, which is the pair every desktop already reads as those two severities; a fold's chevron is `go-down-symbolic` open and `go-next-symbolic` shut, the same two the sidebar's disclosures use. The first shipped set is the completion kinds: Adwaita has no glyph for a function, an enum member or a type parameter, so eighteen `lsp-<kind>-symbolic` icons live in the app `GResource` at `/io/github/stroblme/Accent/icons/scalable/actions/` and are found by name like any other icon, `IconTheme::add_resource_path` having been pointed at the prefix at startup. They are [tabler-icons](https://github.com/tabler/tabler-icons) outlines (MIT, `apps/gtk/data/icons/LICENSE.tabler`) with their strokes converted to fills on the 16 px grid, because GTK recolours a symbolic icon by its `fill`. The drawing ring's seven, `tool-pen`, `tool-highlighter`, `tool-eraser`, `tool-line`, `tool-rect`, `tool-circle` and `tool-adjust`, go through the same pipeline but are drawn for accent: the theme has no pen, marker or eraser at all; a diagram's ring reuses the rectangle, circle and line and adds `tool-select`, tabler's `pointer`, beside Adwaita's `insert-text` and `insert-image`, and the header's Drawing toggle uses `document-edit-symbolic`, the pencil, which it does have. The file types are the third set, and **every file list leads its rows with one** — the Files tree and its vault row, the palette's file rows, the Git pane's folders, changed files and a commit's files, search results, the files under a tag and References — while the tabs carry none. `accent_core::path::file_type` reads the kind off the name (note, PDF, diagram, table, image, code, config, text, anything else) and `doc::icon_for` names the icon: tabler's `markdown`, `file-type-pdf`, `sitemap` (a diagram), `file-spreadsheet`, `photo`, `file-code`, `file-settings` and `file-text` as `filetype-<kind>-symbolic`, and the completion kinds' own folder and file aliased in the GResource as `filetype-folder-symbolic` and `filetype-file-symbolic`. The PDF one letters `PDF` into the page, which at 16 px reads as a shape more than as letters; it was kept over `file-description`, which is `file-text` with one line fewer and would leave a PDF and a text file looking alike. The prefix is `filetype-` and not `file-` because a GResource path is searched as part of hicolor, after the user's theme, so a name the theme also has is the theme's drawing — and themes do use `file-*` (WhiteSur ships `file-link-symbolic`). A GResource rather than hicolor so that a run from the source tree has them too, and the same pipeline is what any further shipped glyph goes through.

**The name is ours, the artwork is not.** An icon theme may replace any Adwaita name, and what it ships may not render: the Replace toggle used `pan-down-symbolic` and was invisible for a user on WhiteSur, whose copy of that file is the one in the theme written with single-quoted attributes (`fill='#363636'`), which GTK4's symbolic recolouring does not parse. The button drew nothing, with no warning on the console. So prefer a name that says what the control does over one that says which way a panel opens: `edit-find-replace-symbolic` is worth more than a chevron even before the bug, and a generic shape is the easiest thing for a theme to have redrawn. The Git pane's disclosures used `pan-down-symbolic` and `pan-end-symbolic`, which WhiteSur ships in that same broken form, and are `go-down-symbolic` and `go-next-symbolic` now, the fold chevrons' pair. libadwaita's own stylesheet still draws the `pan-*` names for a tree expander and a dropdown's arrow, so those are the theme's problem to be worked around rather than a name of ours (NOTEPAD).

## States

- Empty: `AdwStatusPage` with a symbolic icon, a header-capitalised title, one sentence of body text and at most one button (<https://developer.gnome.org/hig/patterns/feedback/placeholders.html>). In the sidebar add `.compact`, or the icon alone takes 128 px of a 200 px column.
- A context menu never scrolls. GTK re-presents a popover only when its parent is allocated, and a widget with a custom `size_allocate` such as `GtkListView` never does, so a menu hung off one freezes at its first-frame size and `GtkPopoverMenu`'s inner scrolled window turns the difference into a scrollbar. Parent it to a plain box instead, and translate the pointer position into that box's coordinates.
- Loading: the status bar's progress text, as `start_reconcile` already does ("Indexing… 1200/42700 files"). Indexing and saving never block the window, so no spinner covers content and no progress bar owns the window. Two bars are drawn, and no third without a line in this file. The first is the sidebar's search progress, a thin pulse above the results while a query is on its worker thread; it belongs to the list it is about to replace, not to the window, and it is held back for the first two pulses so that a query nobody asked for — the requery a changed file triggers under a finished search — is over before there is anything to see. The second is a remote vault's first connection (`connect.rs`), across the top of the document column, which is the surface that wait is about to make usable: determinate while the server binary uploads, because that step knows how far it has got, and pulsed through the steps that do not. GTK4 has no indeterminate mode, so both pulses are a timer of ours, and every one of them is removed when the work ends and when its widget's window closes — a leaked `glib::timeout` keeps firing.
- Toast for a thing that happened and is over ("Saved", "Moved to Trash" with an Undo button). Banner for a state that persists and needs a decision ("This file changed on disk", "A sync conflict copy of this file exists"). A conflict raises the banner on the tab showing the file it concerns, any text file and not only a note, never a toast per conflict copy in the vault: on a synced vault that was a wall of them at startup. Conflicts on files nobody has open are counted on the end of the "Indexed N files" toast instead. The same rule covers the vault worker's own failures — indexing, link resolution, watching — which are index maintenance nobody can act on and which recur for as long as their cause does: each distinct one is said once per vault and logged every time (`Worker::fail`), because an autosave that failed to index raises the same toast on the next keystroke, and the next. `AdwAlertDialog` only when the choice can lose data: overwrite, discard, delete permanently. The sidebar's Replace All is one of those — it rewrites files in place, ones nobody has open — so past a single match it asks first, and the one match already on screen struck through goes through on the click. <https://developer.gnome.org/hig/patterns/feedback/toasts.html> · <https://developer.gnome.org/hig/patterns/feedback/banners.html> · <https://developer.gnome.org/hig/patterns/feedback/dialogs.html>
- A remote vault that stops answering is a banner across the window, every tab being affected and the state lasting. A link that was up comes back on its own: the banner counts down to each attempt — "Lost the connection to host · Reconnecting in 8 s", ticking — after 1, 2, 4, 8 and 16 s and then every 30 s, and each of those attempts is made with `BatchMode=yes`, so it can fail but never raises a passphrase dialog over whatever the reader is doing. Its button is Reconnect Now, the one attempt that may ask. A first connection that failed had nothing to come back to, and an outage past ten minutes is not coming back by itself, so both keep a plain Reconnect button under the last reason. A mistyped path is one such failure: `serve` refuses a root that is not a folder and answers the `hello` with why, so the banner reads "cannot open the vault on host: /srv/x is not a folder" rather than showing an empty vault. A refusal is not a dropped link, and no attempt changes it until someone changes the host, so one that answers an automatic attempt — the folder removed while the link was down — stops the countdown there and keeps the plain Reconnect. While a remote window's stored tabs wait for the host, the empty document column says how many ("Waiting for host", "3 tabs will open when it answers.") rather than No Note Open, and a window closed before its host ever answered leaves the stored session as it found it. Its tree says the same until the host has listed the root ("Waiting for host", "Its files will show here when it answers."), rather than Empty Vault. A window without a vault has no banner: its remote tabs say for themselves when the link went, and come back on a key press.
- A file that will not open as text raises neither a dialog nor a toast: its tab holds an `AdwStatusPage` instead, for a binary file (a NUL byte in the bytes, the same test `grep` and `git` use) and for anything over the 16 MiB `fs::MAX_TEXT` cap. The file is what failed, so the failure belongs in that file's own tab and stays there until the tab is closed, rather than in a message that has to be dismissed before the window is usable again. That is the open itself; anything that was waiting on the file to become a tab — a comparison, a jump to a match (`App::with_tab`) — has nowhere left to run and is said in a toast ("Cannot compare notes.png: binary file"), because the status page answers the open and says nothing about what else was asked for.
- A file that is text but not valid UTF-8 opens read-only behind a banner with no button. What is on screen is a lossy reading of the bytes, so the only safe answer is to leave the file alone, which is what the tab already does; a banner is a state that persists, and not every state has an answer to offer.
- A tab has one banner and can have more than one thing to say about its file, so the questions queue rather than overwrite each other, and the bar shows the one that can cost most: "deleted on disk", then "changed on disk", then a sync conflict copy (which blocks nothing), then the read-only report (which asks nothing). Taking one down brings the next back up instead of clearing the bar — a conflict copy appearing used to wipe the "changed on disk" question, and resolving that copy then took the bar away with the wiped question still standing, leaving a tab that would never autosave again and nothing on screen to say why. Queued and not merged: `AdwBanner` has exactly one button, and two questions on one line have no honest single label.
- **Saving never answers a question.** A buffer whose file moved underneath it holds the only copy of both its edits and the answer the user has not given, so nothing writes until they give it — VS Code's rule, and `editor::may_save` is the one predicate every save path asks. Autosave becomes a plain no-op, with the banner and the tab's dot as the only signal: it cannot raise a modal on every focus change and idle second, and it deliberately does not write the buffer anywhere else either, because a copy nothing in the app ever reads back is a second source of truth. Ctrl+S refuses too, and says so with the overwrite dialog (or, over a note deleted on disk, by writing it back, which is what that banner's button already offers). The two paths a tab leaves by are the exception: a tab closing and a window closing still attempt the write and ask when it is refused, because a buffer on its way out has nowhere else to be kept and refusing there would lose it outright. Underneath all of it the etag gate in `fs::write_note` has the last word, and a failed `stat` is never read as a change — "I could not find out" is not "someone else wrote this".
- **Closing while git works.** A command that rewrites the working tree or the index — a pull, which is the first half of every Sync, a merge, a switch, a commit, Stage, Unstage, Discard, Abort Merge — cannot be cut off without leaving the repository half-updated, so closing the window then asks: "Git Is Updating Files", with Cancel and Close When Finished, the second suggested and no answer that stops git. Waiting says "Closing when git has finished…" in the status bar and closes the window once the command lands; one that fails keeps the window open under its own failure. The question comes before any buffer is flushed, so the flush and the Unsaved question run on the files git left behind. A fetch and the push half of a Sync are stopped instead and the window closes at once: a fetch moves remote-tracking refs and nothing else, and a remote takes a push whole or not at all, so the commits a stopped push did not send are the ahead count the next fetch shows, and nothing else says so. On a remote vault the host runs git and only it knows which half a Sync is in, so a Sync there asks all the way through, and a fetch is left to the host, which ends it within its own bound once the link closes.

## Motion

libadwaita defaults only: no custom easing, no staggered reveals, nothing that animates on load. The only timings we own are debounces, and they exist to keep the main loop free.

The document follows the caret and nothing else. The view is the scrolled window's scrollable child, so GTK keeps the insert mark on screen by itself — arrow keys, typing, find, Go to Line, a search hit and every extra caret land in view without anyone asking. Nothing else moves the viewport: a wheel scroll away from the caret stays where it was put, and a dialog opening and closing over it puts nothing back.

## Pre-flight checklist

Ten mechanical checks before shipping a UI change. None of them needs judgement.

1. `cargo fmt --all --check`
2. `cargo clippy -p accent --all-targets --locked -- -D warnings`
3. `cargo test --locked && cargo test -p accent --locked`
4. Headless smoke run: `make smoke` (its `XVFB_ENV` carries `GDK_BACKEND=x11` and `GTK_A11Y=none` as well as `G_DEBUG=fatal-criticals`; see ROADMAP §6 for why each is load-bearing)
5. Dark: `gsettings set org.gnome.desktop.interface color-scheme prefer-dark`, look, then set it back to `default`
6. Accent: `gsettings set org.gnome.desktop.interface accent-color teal`, look, then set it back to `blue`
7. No stray colours: `grep -rnE '#[0-9a-fA-F]{3,8}' apps/gtk/src | grep -v theme.rs` returns nothing
8. Reduced motion: `gsettings set org.gnome.desktop.interface enable-animations false`, check nothing became unreachable, then set it back to `true`
9. Keyboard-only pass with the pointer unplugged: reach every action in the accelerator table, and get the auto-hidden chrome back without a mouse
10. `GDK_SCALE=2 target/release/accent testvault` for scaling, plus an IME check (ibus, type CJK into a note and confirm the preedit lands in the right place)
